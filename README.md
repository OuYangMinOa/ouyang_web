# ouyang_web

Rust（Axum + SQLite）後端 + React（Vite）前端，打包成單一 Docker image 部署。

```
frontend/   React + Vite + TypeScript
backend/    Axum + sqlx（SQLite），同時提供 /api 與前端靜態檔
deploy/     伺服器上用的 compose.yaml、各環境設定、deploy.sh
Dockerfile  多階段建置：前端打包 → cargo-chef 編譯 → distroless 執行
```

## 本機開發

```shell
# 後端（:8080，資料庫在 backend/data/app.db）
cd backend
cargo run

# 前端（:5173，/api 會 proxy 到 :8080）
cd frontend
npm install
npm run dev
```

測試：

```shell
cd backend && cargo test
cd frontend && npm run lint && npm run build
```

後端的整合測試（`backend/tests/`）全部編成同一個執行檔 `integration`：每個檔案各一個執行檔的話，每個都要連結一次整個後端，
cargo 也一次只跑一個，CI 上光這兩項就多一分鐘以上。新增測試檔要在 `tests/main.rs` 加一行 `mod`，漏了的話 `every_test_file_is_listed` 會失敗。
只跑某個檔案：`cargo test --test integration bigtwo::`。

資料庫 migration 放在 `backend/migrations/`，服務啟動時自動執行。

## 登入與權限

```
使用者 ──user_roles──▶ 角色 ──role_permissions──▶ 權限
alice                  admin（系統管理員）         admin.users
```

- 密碼用 argon2id 雜湊；session 是隨機 token 放在 HttpOnly cookie（`session_<env>`），資料庫只存 token 的 SHA-256，7 天過期。
- 同一個 IP 15 分鐘內登入失敗 10 次會暫停登入。拿過假 `.env` 的 IP 24 小時內不能登入和註冊（見 [.env 蜜罐](#封鎖)）。
- 停用帳號、重設密碼會讓該帳號所有裝置登出；自己改密碼只保留目前這個裝置。
- 管理員不能停用自己或移除自己的 `admin` 角色，避免把自己鎖在外面。
- 自行註冊：預設關閉，管理員在 `/admin/registrations` 開關。開放時登入頁會出現「註冊」按鈕，送出的申請要管理員核准才會建立帳號（沒有任何角色）。同一個 IP 一天最多申請 3 次。

頁面：`/login` 登入、`/register` 註冊、`/account` 改密碼、`/feedback` 回報與許願、`/admin/users`、`/admin/roles`、`/admin/registrations`、`/admin/feedback`、`/admin/access`、`/admin/visits`、`/admin/honeypot`、`/admin/games`、`/admin/draw-words`、`/admin/system`、`/admin/ai`、`/admin/ai-tools`、`/admin/ai-usage` 系統管理（需要 `admin.users`，沒有權限的人在選單裡看不到）。

### 回報與許願

頁首右上角的「💬 回報 / 許願」進 `/feedback`，每一筆是一串對話，管理員在 `/admin/feedback` 回覆、結案或刪除，雙方可以一直來回留言（`backend/src/feedback.rs`）。

- 不用登入也能送：訪客第一次送出時會拿到 HttpOnly cookie `feedback_<env>`（Path 只到 `/api/feedback`），之後靠它認出自己的對話。登入的人用帳號，也看得到同一個瀏覽器先前以訪客身分送出的。
- 圖片可以 Ctrl+V 貼上、拖曳或選檔。一貼上就先上傳（`POST /api/feedback/images`，body 是圖片本身，上限 5 MB；太大的前端會先縮小成 WebP），送出留言時才掛上去，一天內沒掛上的會被清掉。
  後端看檔頭只收 PNG / JPEG / GIF / WebP，圖片存在 SQLite（`feedback_images`），只有對話雙方和管理員看得到。
- 未讀：雙方各記看到哪一則，頁首的紅點是有新回覆的對話數；管理員的紅點還包含使用者的新留言。頁面開著時每 20 秒看一次有沒有新留言。
- 同一個 IP 一天最多開 10 串、留 100 則、傳 60 張圖（管理員不受限）。

### 建立或救回管理員

帳號已存在時會重設密碼、重新啟用並加回 `admin` 角色。密碼從 stdin 讀，不會留在指令列或 shell 歷史裡：

```shell
# 本機
cd backend && cargo run -- create-admin admin

# 伺服器（<env> 是 staging 或 prod），輸入密碼後按 Enter
cd ~/ouyang_web/<env> && docker compose exec -T app /app/backend create-admin admin
```

### 新的 APP 要加權限時

1. 新增 migration，登記權限並授權給角色：
   ```sql
   INSERT INTO permissions (name, description) VALUES ('notes.write', '編輯筆記');
   INSERT INTO role_permissions (role_id, permission) SELECT id, 'notes.write' FROM roles WHERE name = 'admin';
   ```
   需要新角色就 `INSERT INTO roles (name, description) VALUES ('editor', '編輯者');`。
2. 在 `backend/src/auth.rs` 定義權限，handler 參數加上 `Require<NotesWrite>`，沒登入回 401、沒權限回 403：
   ```rust
   pub struct NotesWrite;
   impl Permission for NotesWrite {
       const NAME: &'static str = "notes.write";
   }

   async fn create_note(Require(user, _): Require<NotesWrite>, ...) { ... }
   ```
3. 前端用 `useAuth().can('notes.write')` 決定要不要顯示，用 `<RequireAuth permission="notes.write">` 保護頁面。前端的判斷只是介面，真正的檢查在後端。

### 新增 APP

1. 在 `frontend/src/apps/registry.ts` 的 `APPS` 加一筆：`id`（網址前綴）、名稱、圖示、首頁卡片文字，以及 `nav`（側邊欄的頁面，可以分組）。需要權限才能用的 APP 設 `permission`，沒權限的人在切換面板和首頁都看不到；只要登入就能用的設 `loginOnly`；需要大畫面的（小遊戲）設 `wide`，內容區從 1000px 放寬到 1440px。
2. 在 `App.tsx` 把路由包在 `<AppLayout />` 底下（要權限就再包一層 `<RequireAuth>`）：
   ```tsx
   <Route path="/notes" element={<AppLayout />}>
     <Route index element={<NotesList />} />
     <Route path=":id" element={<NoteEditor />} />
   </Route>
   ```
   桌機的側邊欄固定在畫面最左邊（可收合成只剩圖示），內容區在剩下的寬度裡置中；窄於 900px 時改成頁首的「APP › 頁面 ▾」選單。
   兩邊都是 `frontend/src/components/SideNav.tsx`：頁面有 10 個以上時，上面會出現搜尋框（Enter 直接開第一個結果、Esc 清掉），
   每一列右邊可以釘選，釘選的排在最上面。沒登入存在瀏覽器，有登入存在帳號（`GET /api/nav/pins`、`PUT /api/nav/pins/<APP id>`，`backend/src/nav_pins.rs`），換裝置也一樣。

> prod（`https://ouyang.app`）和 staging（`https://test.ouyang.app`）都走 HTTPS，`<env>.env` 設了 `COOKIE_SECURE=true`。
> cookie 沒有設 Domain，只屬於各自的網址，名稱也依環境分開（`session_<env>`），兩邊的登入互不影響。

## 外觀：風格與深淺

頁首右上角的「🎨 外觀」打開對話框（`frontend/src/components/Appearance.tsx`），選了馬上套用，存在瀏覽器的 localStorage（不跟帳號走），別的分頁也會跟著換。

| | 亮色 | 深色 |
|---|---|---|
| **墨與陽**（預設） | 宣紙上的墨，強調色是太陽的橘 | 夜裡的餘燼 |
| **塗鴉** | 方格筆記本：原子筆藍、螢光筆黃 | 深灰黑板：粉筆白、粉筆黃 |

- 深淺是 `<html data-theme>`、風格是 `<html data-style="doodle">`，`index.html` 在畫面出來前先套上，避免閃一下預設的樣子。
- 色票在 `index.css`：塗鴉只換基本色（`--bg`、`--text`、`--accent`…）、字型和形狀變數，遊戲棋盤這類專用色沿用墨與陽的亮色／深色。
- 塗鴉的形狀在 `doodle.css`：歪歪的圓角、筆畫框線、錯開的實心陰影、頁首手畫的底線。權重跟 `App.css` 的基本樣式一樣，各頁面能蓋過基本樣式的地方，塗鴉時一樣蓋得過去。
- 便條紙、外觀對話框和首頁太陽的框線會微微抖動：SVG 濾鏡 `#doodle-rough`（`components/DoodleDefs.tsx`），只套在框線上，字不會跟著抖。
- 字型都來自 Google Fonts，只有選了塗鴉才載入，也是依用到的字分片下載：
  - 全站的標題和內文統一用圓體「粉圓」（Huninn），筆畫粗細一致、讀久不累。`--sans` 和 `--serif` 都指向它，頁面不用另外處理。
  - 只有首頁的名字和左上角的站名當 logo，用手寫字「芫荽」（Iansui，變數 `--hand`）。芫荽只有一種粗細，用的地方要寫 `font-weight: 400`，不然瀏覽器會硬加粗，筆畫會糊在一起。
- 首頁的 3D 粒子太陽在塗鴉風格換成手畫的笑臉太陽（`components/DoodleSun.tsx`），不載入 three.js。
- 外觀設定裡的縮圖用 `data-preview="<風格>-<深淺>"` 把那一組變數套在縮圖上，所以不管目前選哪個，縮圖都畫得出另一種的樣子。

## 小遊戲線上對戰

> 遊戲頁的盤面大小用 `games.css` 的 `--game-vh`（視窗扣掉頁首和標題列後剩的高度）或 `--board-vh`（再扣掉一行狀態和一排按鈕）來算，
> 不要寫死 `100dvh - …`，整個遊戲才不用捲動就看得完（在遊戲室裡、窄螢幕標題列換成兩行也一樣）。

後端只負責轉送訊息，不懂遊戲規則；規則由兩端各自執行（`frontend/src/games/shared/useRoom.ts`、`backend/src/games.rs`）。不需要登入，但登入後會用帳號認座位。

```
POST /api/games/rooms  {"game":"gomoku"}  →  201 {"code":"ABCDE"}      game：gomoku / xiangqi / chess / reversi / connect4 / ab / battleship
GET  /api/games/rooms/{code}/ws?game=<id>&player=<id>                  升級成 WebSocket（登入時 player 可省略）

client → server  {type:"msg", data}
server → client  {type:"welcome", seat, peer, history:[{seat, data}]}
                 {type:"welcome", seat:null, online:[bool,bool], history}   觀戰
                 {type:"peer", online}                  對手上線／離線（給坐著的人）
                 {type:"online", online:[bool,bool]}    兩個座位的連線狀態（給觀戰的人）
                 {type:"watchers", count}               觀戰人數變了
                 {type:"msg", seat, data}
                 {type:"error", code, message}   之後伺服器關閉連線
```

- 每個房間兩個座位，重連時用 player 拿回同一個座位，並收到完整歷史。**登入的人一律用帳號（`user:<id>`）**，換分頁或裝置都拿得回座位；
  訪客才用 query 的 `player`（前端每個分頁產生一個，存在 sessionStorage），伺服器存成 `guest:<player>`，所以冒用不到帳號的座位。
  之後新增的多人遊戲也要沿用這個規則。
- 同一個 player 從別處連進來時，舊連線會收到 `replaced` 錯誤後被關掉，前端不再自動重連（避免兩個分頁互踢），改顯示「在這裡繼續」。
- 任何一方送出的訊息，伺服器加上 seat 後依序存進歷史並廣播給兩邊（包含送出者）和觀戰的人，所以大家看到的順序完全一樣。
- **觀戰**：兩個座位都有人之後，其他人連進來就是觀戰（`seat` 是 null），先收到完整歷史，之後每一步都收得到，但送出的訊息伺服器不理。
  不需要另外的網址，打開同一個房間連結就行；一間最多 50 人觀戰，超過才回 `full`。觀戰的人不佔座位、不用 player 認人，
  所以同一個人開兩個分頁也沒關係。只有觀戰的人連著時房間也不會被收掉。
  前端的 `room.spectator` 為 true 時各遊戲只顯示局面、不顯示認輸／悔棋／再來一局；海戰棋和 1A2B 的祕密照樣只在兩位玩家的瀏覽器裡，
  觀戰的人和對手看到的一樣多，結束公開後才看得到全部，並一樣驗證雜湊。
- 五子棋、四子棋、黑白棋、象棋、西洋棋的線上悔棋要對方同意（`frontend/src/games/shared/takeback.ts`）：事件是 `takeback`、`takeback-accept`、`takeback-decline`、`takeback-cancel`，
  一樣只在兩端的 reducer 裡處理，後端不用改。退回到提出的人上一次輪到自己的局面（1 或 2 手）；請求中雙方都不能下，被拒絕後要等下一手才能再提，對局結束就不能悔棋。
- 連線一律先升級，有問題再送 `error` 後關閉（瀏覽器讀不到升級失敗的 HTTP 狀態）：`not_found`、`game_mismatch`、`full`（觀戰的人太多）、`bad_request`、`replaced`、`internal`，
  以及送太快（每秒超過 20 則）的 `rate_limited`、太大（data 超過 4KB）的 `too_large`、歷史超過 2000 筆的 `history_full`。
- 伺服器每 25 秒送一次 ping；60 秒沒收到任何東西就當作斷線。
- 沒有人連線超過 30 分鐘、或建立超過 24 小時的房間就失效，並在下次有人建立房間時從資料庫刪掉。房間最多 1000 個，超過回 503。
- 房間、座位和歷史存在資料庫（`game_rooms`、`game_events`），記憶體只放有人連線中的房間。重啟或換版後，前端自動重連就能接著下。
- 換版的幾秒內新舊容器可能各有同一個房間的連線：座位用條件式 UPDATE 搶，事件用 `(room_code, seq)` 主鍵擋重複序號。
  寫入時序號撞到，就關掉那個容器裡這個房間的連線，前端重連後從資料庫重新載入，送出的那一步要重下。

### 海戰棋

`/games/battleship`：也用上面的轉送房間，但佈局是祕密，不能放進會廣播給雙方的訊息（`frontend/src/games/battleship/`）：

- 開局各自送出 `commit = SHA-256(佈局 + 隨機 salt)`，佈局和 salt 只存在自己的瀏覽器（localStorage，用房間、座位、局數和雜湊當 key，重連時拿回來）。
  雜湊用 `hash-wasm`，因為 `crypto.subtle` 只在 HTTPS 能用。
- 每一砲由被打的一方自己算出「沒中／擊中／擊沉」回報，擊沉時公布那艘船的位置；位置不合理（和先前的回報對不上）當場判亂報的一方輸。
- 結束後雙方自動公開佈局和 salt，前端驗證雜湊和過程中的每一次回報，對不上就判對方輸。換裝置或清掉瀏覽器資料就拿不回佈局，只能認輸。

### 1A2B 對戰

`/games/ab` 的「對戰」：雙方各藏一組數字輪流猜，可以對電腦（三種難度）或線上。線上一樣走上面的轉送房間，
但轉送伺服器會把訊息給雙方看，所以祕密數字絕對不送出去（`frontend/src/games/ab/versusRules.ts`）：

- 開局各自送 `commit = SHA-256("數字:salt")`（salt 是 16 bytes 亂數，不能靠 5040 種窮舉回推；用 `hash-wasm`，http 的 staging 也能算）。
- 對方猜了，由被猜的那一方的瀏覽器用自己的數字算 A／B 自動回報；數字和 salt 存在 localStorage（連 commit 一起存），重連後重播歷史也回報得了。
- 分出勝負後雙方公開數字和 salt，用戶端驗證雜湊和每一次回報，對不上就判那一方輸。換了裝置找不到自己的數字時只能認輸。

### 俄羅斯方塊 99

`/games/tetris`：參考 Tetris 99 的大逃殺，一間最多 99 人，人不夠由電腦補位。和上面的棋類不同，伺服器懂一部分規則
（`backend/src/arena.rs`，和魔法氣泡共用；俄羅斯方塊的盤面格式和電腦玩家在 `tetris.rs`。協定寫在 `frontend/src/games/shared/useArena.ts`）：

```
POST /api/games/tetris/rooms  {"public":true}  →  201 {"code":"ABCDE"}   public：快速配對，加入正在等人的公開房間，沒有就開一間
GET  /api/games/tetris/rooms/{code}/ws?player=<id>&name=<暱稱>           升級成 WebSocket（登入時用帳號與帳號名稱）
```

- 每個人的盤面在自己的瀏覽器裡跑（`engine.ts`：SRS、7-bag、T／L／J／S／Z／I 的 spin、連擊、B2B），伺服器只收攻擊行數、盤面快照和出局，
  負責選目標（隨機／快輸的／徽章／反擊，或手動點小盤面）、轉送垃圾行、算 KO、徽章、名次與速度等級，以及模擬電腦玩家。
- 房間每 250ms 推進一次，這段時間的狀態和盤面變化合併成一則廣播。
- 電腦玩家沒有真的在下方塊，是用機率模擬放塊、消行和被攻擊推高。大部分是弱的，前期就會陸續出局；每 7 個有 1 個強的（至少一個）撐到後面。
  等級越高越容易失誤，只剩電腦時大約四、五分鐘分出勝負。調整時用 `cargo test --release pacing -- --ignored --nocapture` 看每個時間點出局了幾個。
- 房間只放在記憶體：**重啟或換版時進行中的對局會中斷**。沒人連線 2 分鐘就收掉，最多 200 間。
- 對局中斷線 10 秒判出局；重新整理後手上沒有這局的盤面，會直接認輸、等下一局。
- 觀戰：每個人可以在房間的大廳選「上場／觀戰」（`{type:"watch", watch}`），選了觀戰的人開局時不參戰、不佔 99 人的名額，
  畫面改成把上場的人的盤面放大排出來（`WatchBoards`，手機上兩個並排），電腦在下面用小盤面。至少要一個人上場才能開局（只剩電腦會馬上結束）。
  對局中改選的話下一局才生效。
- 單人模式每消 10 行或每玩 1 分鐘升一級（看哪個先到），沒有上限；分數照官方規則（消行、spin、B2B、連擊、全消乘上等級，加上下落格數）。
  下落速度第 1 級 1 秒一格、每級乘 0.82（第 29 級約 4ms 一格），第 30 級起是 20G：方塊出生、移動、旋轉後都直接落到底，只能靠鎖定延遲調整。對戰的等級最高 15，不會到 20G。
  登入的人的成績會上傳到排行榜（`backend/src/tetris_scores.rs`，每個帳號只留最高分）：

  ```
  GET  /api/games/tetris/scores                 →  {"top":[{rank,username,score,lines,level,duration_ms,achieved_at}],"me":{…}|null}
  POST /api/games/tetris/runs                   →  201 {"id"}   開局，伺服器記下開始時間（要登入，一個帳號同時一局）
  POST /api/games/tetris/runs/{id}/checkpoints  {"score","lines","level","pieces","duration_ms","board"}  →  204
  POST /api/games/tetris/runs/{id}/finish       同上  →  排行榜再加 "best"（有沒有刷新紀錄）
  ```

  分數是前端算的，伺服器不重播整局，而是每 5 秒（遊戲時間）檢查一次中間態來確認真的有玩：遊戲時間不能超過實際經過的時間、
  數字只增不減且增加速度合理、盤面沒有滿行且格數等於「方塊數 × 4 − 行數 × 10」。有一次不合理整局作廢。
  進行中的局只放在記憶體，重啟或換版時正在玩的那局無法上傳。
- 背景音樂是 Korobeiniki（俄羅斯民謠），用 Web Audio 即時合成（合成器在 `games/shared/music.ts`，曲子在 `tetris/music.ts`），不需要音檔：三角波旋律、正弦波低音，
  加上低通濾波和一點回音讓聲音柔和；速度跟著等級變快，按 M 或按鈕開關，按鈕旁的喇叭可以調音量。
  開關和音量（`games:music`、`games:musicVolume`）存在瀏覽器的 localStorage，所有小遊戲共用，不跟帳號走。
- 音效也是即時合成（`tetris/sfx.ts`），開關和音樂分開：移動、旋轉、保留、鎖定、直接落下、消行、垃圾行升起各有一個短音。
  旋轉後卡在 spin 的位置會多一聲高音的「叮」，還沒放下就知道卡對了。引擎把要發的音效放進 `sounds`，盤面每一幀取走，同一幀一樣的只響一次。
- 按下加速下落的瞬間先掉一格，之後照操作手感設定的間隔（預設 30ms）一格。
- 快捷鍵可以自訂（`games/shared/keys.ts`、`games/shared/KeyEditor.tsx`，和魔法氣泡共用），每個動作最多兩個鍵。沒登入存在瀏覽器，有登入存在帳號（`backend/src/game_settings.rs`），
  換裝置也一樣；帳號還沒存過時沿用瀏覽器的設定：

  ```
  GET /api/games/tetris/settings  →  {"keys":{"left":["ArrowLeft"],…}|null}   null 是沒存過（要登入）
  PUT /api/games/tetris/settings  {"keys":{…}|null}  →  204                   null 是恢復預設
  ```

- 操作手感也可以調（`games/shared/handling.ts`、`games/shared/HandlingEditor.tsx`）：DAS 是左右鍵按住多久開始連續移動（50～400 ms，預設 180），
  ARR 是之後每格的間隔（0～200 ms，預設 40，0 是直接滑到底）。按下先走一格、按住滿 DAS 走第二格，時間從按下的那一刻算，不受每幀長短影響。
  加速下落間隔（soft，0～100 ms，預設 30）是按住下時每格的間隔，0 是瞬間落到底但不鎖定，按住時移動、旋轉後也會馬上落到底（和 20G 一樣）。
  存法和快捷鍵一樣，但分開存（`game_handling` 表）：

  ```
  GET /api/games/tetris/handling  →  {"handling":{"das":180,"arr":40,"soft":30}|null}   舊資料沒有 soft 時當作 30
  PUT /api/games/tetris/handling  {"handling":{…}|null}  →  204   超出範圍回 400
  ```

### 魔法氣泡

`/games/puyo`：參考ぷよぷよ通的規則，有單人模式、一對一對戰電腦（全部在瀏覽器裡跑，`frontend/src/games/puyo/`），
以及和俄羅斯方塊一樣的大逃殺。和俄羅斯方塊共用快捷鍵、背景音樂合成器、排行榜和大逃殺的元件（`games/shared/`）。

- 規則（`engine.ts`）：6 × 12 的盤面加上看不到的第 13 列，兩顆一組、四種顏色，同色 4 顆以上相連就消掉，可以連鎖。
  分數照官方公式：10 × 消掉的顆數 × (連鎖倍率 + 連結加成 + 顏色加成)。第 3 欄最上面被堵住就輸。
  消除和掉落是有時間的動畫，連鎖一步一步推進，看得到每一連。
- 對戰：兩邊用同一個亂數種子，拿到一樣順序的氣泡。每 70 分換一顆干擾泡，先抵銷自己待落下的再送出去；
  開打 96 秒後進入加時，換算分數每 16 秒變成 3/4。全消後下一次連鎖多送 30 顆。
- 電腦（`cpu.ts`）：每組把所有落點（最多 22 種）都模擬一次，看現在能不能打出夠大的連鎖、「再補一兩顆能引爆幾連鎖」和盤面形狀；
  困難再把下一組也考慮進去（只從最好的 8 個落點往下看，手機上不會卡）。三種難度差在想多久、動多快、要等幾連鎖才引爆。
- 單人模式每放 30 組或每玩 1 分鐘升一級。登入的人的成績會上傳到排行榜（`backend/src/puyo_scores.rs`），做法和俄羅斯方塊一樣檢查中間態：

  ```
  GET  /api/games/puyo/scores                 →  {"top":[{rank,username,score,max_chain,level,duration_ms,achieved_at}],"me":{…}|null}
  POST /api/games/puyo/runs                   →  201 {"id"}
  POST /api/games/puyo/runs/{id}/checkpoints  {"score","level","pieces","popped","lost","max_chain","duration_ms","board"}  →  204
  POST /api/games/puyo/runs/{id}/finish       同上  →  排行榜再加 "best"
  ```

  伺服器檢查：盤面沒有懸空的氣泡、沒有該消沒消的四連、顆數等於「組數 × 2 − 消掉的 − 疊出界的」；
  分數增加不超過「消掉的顆數 × 9990」（倍率上限 999）加上下落與全消的分數。前端只在有一組在操作時回報（連鎖途中的盤面還沒算完）。
- 大逃殺（`backend/src/puyo.rs`）：房間、選目標、KO 和徽章和俄羅斯方塊共用 `arena.rs`，只能用房間代碼或邀請連結加入（沒有快速配對）。
  攻擊單位是干擾泡顆數，盤面是 13 × 6 個 `0`～`5`（含看不到的第 13 列，`5` 是干擾泡）；速度等級最多用到 10：

  ```
  POST /api/games/puyo/rooms  →  201 {"code":"ABCDE"}
  GET  /api/games/puyo/rooms/{code}/ws?player=<id>&name=<暱稱>
  ```

  電腦玩家每一手放兩顆，其中一部分「有用」，存夠了就引爆一串連鎖（強的打得比較長），干擾泡照前端的公式換算（含加時）；
  弱的放得亂，沒用的氣泡越積越高。
- 背景音樂是另外寫的一段輕快小曲（`puyo/music.ts`），不是原作配樂。快捷鍵存在 `/api/games/puyo/settings`（格式同俄羅斯方塊）。

### 派對房間

給「有隱藏資訊、3～10 人、回合制或計時」的遊戲用（誰是臥底、踩地雷競速，之後的大老二、你畫我猜…）。和上面兩種房間都不同：
規則全部在伺服器（`backend/src/party.rs`），用戶端只送「我想做什麼」，伺服器驗證後改狀態，再把**每個座位各自的視角**送出去，
別人的牌、別人的詞根本不會離開伺服器。協定寫在 `frontend/src/games/shared/useParty.ts`，大廳、聊天等元件在 `games/shared/Party.tsx`。

```
POST /api/games/<遊戲>/party              →  201 {"code":"ABCDE"}
GET  /api/games/<遊戲>/party/{code}/ws?player=<id>&name=<暱稱>
```

- 房間只放記憶體：伺服器重啟或換版時進行中的房間會消失（用戶端會收到「房間已經關閉」）。沒人連線 5 分鐘後清掉，最多 200 間。
- 第一個進來的人是房主，離開就輪到下一個人（從遊戲室開的房間照遊戲室的順序，見下面的「遊戲室」）。房主可以改選項、加減電腦玩家、請人離開（之後不能再進來）、開始和中止。
  加電腦是 `{type:"addBot", count?}`：一次加 `count` 台（沒填是 1 台），座位或電腦數滿了就停；電腦上限 10 台以上的遊戲（機甲對戰）大廳多一顆「補滿電腦」。
  開局時連著線的人加上電腦照名單順序入座，超過人數上限的人和對局中才進來的人觀戰，下一局再加入。一局結束後可以「再來一局」，分數由遊戲自己累計。
- 每個人也可以在大廳自己選「觀戰」（`{type:"watch", watch}`，`players[].watching`）：開局時不入座，人數沒滿也一樣，房主也可以只看不玩。
  用 key 記在房間的 `watchers`，重新整理、還沒連進來（遊戲室先交過來的）也記得；對局中改選的話下一局才生效。
- 認人的方式和大逃殺一樣：登入認帳號，訪客認分頁。對局中斷線的人保留座位，怎麼處理（逾時跳過、自動出手）由遊戲決定。
- 送出去的有三種：每個人自己的 `view`（狀態有變才重送，內容一樣就不送）、遊戲的即時事件 `event`（不存，例如筆畫）、聊天。
  對局中的聊天會先交給遊戲決定誰看得到，例如出局的人只能跟出局、觀戰的人聊。
- 每條連線每秒最多 20 則、一則最多 4 KB（遊戲可以調整），超過就斷線。
- 新增一款遊戲：實作 `PartyGame`（見 `party.rs` 檔頭的步驟）、在 `AppState` 加一份房間表、掛兩條路由，前端用 `useParty` 和共用元件。

### 遊戲室

`/games/room/{code}`：同一群人換著玩不同遊戲，不用每換一款就重開房間、重新邀請（`backend/src/lobby.rs`、`frontend/src/games/lobby/`）。
小遊戲大廳按「開遊戲室」，把連結傳給朋友；房主選遊戲，伺服器替大家開好那款遊戲的房間，所有人自動跳過去，玩完按標題列上的「換遊戲」再選下一款。

```
POST /api/games/lobby                     →  201 {"code":"ABCDE"}
GET  /api/games/lobby/{code}/ws?player=<id>&name=<暱稱>
```

- 遊戲室不懂遊戲規則，只記名單、聊天、每個人要上場還是觀戰（`watch`）和「現在在玩哪一間」（`playing`）。
  能開的遊戲登記在 `lobby.rs` 的 `GAMES`（派對遊戲和大逃殺還要在 `room_table` 對到房間表）和前端 `registry.ts` 的 `lobby`。
- **上場／觀戰**：名單旁每個人自己選（包括房主），房主開遊戲時所有人都跳過去，選了觀戰的人到了那邊不上場、在旁邊看。
  - 派對遊戲和大逃殺：開房時把遊戲室的順序（`hosts`）和選了觀戰的人（`watchers`）交給那間房間，遊戲室的房主到了那邊也是房主，不管誰先連上。
    派對遊戲裡觀戰的人不入座，大逃殺裡不參戰、改看上場的人放大的盤面。
  - 兩人的棋類由房主從要上場的人裡挑誰先手、誰後手（選了觀戰的人不能挑），開房時就把兩個座位排好（`game_rooms.seat0/seat1`），其他人連進去是觀戰。
  - 改選時：在遊戲室改的，正在玩派對遊戲或大逃殺的話伺服器會轉給那一間（`set_watch`）；在遊戲頁的大廳改的，前端也會同步回遊戲室（`useLobbyWatch`），
    兩邊一致，下一款遊戲照這個。都是下一局才生效，這局在場上的人照樣打完。
- 整個小遊戲區（`GamesLayout`）共用一條遊戲室的連線，玩遊戲的時候也連著，房主換遊戲時才跟得過去；連上時已經在玩的那一間不會自動跳，
  遊戲頁標題列上的遊戲室（`LobbyChip`）和大廳最上面的卡片有「回到…」（觀戰的人是「觀戰…」）。
- 棋類、大逃殺這些沒有聊天室的遊戲頁，標題列的遊戲室有「聊天」，打開是浮在右下角的遊戲室聊天（有未讀數），上場和觀戰的人可以邊看邊聊。
  派對遊戲有自己的聊天室（有些話不能讓場上的人看到，例如答案、身分），所以不開。
- 遊戲室開的房間不顯示自己的房間代碼、邀請和離開（`useInLobbyRoom`），大家只看得到遊戲室的代碼，邀請的也是遊戲室，下一款遊戲才跟得到。遊戲室代碼存在 sessionStorage，只認這個分頁。名字和派對房間共用，大逃殺沒取過名字的也用這個。
- 只放在記憶體，伺服器重啟或換版時會消失。斷線的人留在名單上一分鐘，沒人連線 10 分鐘就收掉，最多 200 間、每間 30 人。
  房主開完一間後 2 秒內不能再開（避免連點開出好幾間），可以請人離開（之後不能再進來）。

### 誰是臥底

`/games/undercover`：第一款派對遊戲（`backend/src/undercover.rs`）。大部分人拿到同一個詞（平民），一兩個人拿到相近的另一個詞（臥底），
可以多一個沒有詞的白板（算臥底這邊）。每個人只看得到自己的詞，不知道自己是哪一邊。

- 流程：看詞 → 依序每人一句描述（不能包含自己的詞，伺服器檢查；有發言時間）→ 討論（可以設 0 秒跳過）→ 投票。
  票最多的人出局；平手只在平手的人之間重投一次，再平手這輪沒人出局，投完公開誰投誰。白板出局時可以猜一次平民的詞，猜中臥底這邊直接贏。
- 勝負：臥底和白板全部出局平民勝；臥底這邊的人數追上平民就臥底勝。分數在同一個房間累計（平民贏每人 1 分、臥底這邊贏每人 2 分）。
- 選項：臥底人數（自動是 5 人以下 1 個、6～8 人 2 個、更多 3 個，白板佔一個名額）、白板、線下模式（當面口頭描述，網站只負責發詞、輪流和投票）、
  出局時要不要公開身分、發言和討論的秒數。臥底這邊一定要比平民少，配不出來時不能開始。
- 出局和觀戰的人只能在旁邊聊天，場上的人看不到；聊天裡直接說出自己的詞不會送出。
- 詞庫在 `backend/src/undercover_words.txt`（160 多組，每個詞附幾句描述）。電腦玩家發言時從自己那個詞的描述裡挑一句，白板電腦用通用的模糊描述；
  投票看誰的描述和自己的詞最不像，再加上跟票。電腦只知道自己的詞，跟真人一樣。

### 古董局中局

`/games/antique`：6～8 人的身分推理派對遊戲（`backend/src/antique.rs`），改編自同名桌遊，只做基本的 8 個角色（沒有粉絲角色）。
許愿陣營（許愿、方震、黃煙煙、木戶加奈、姬雲浮）要找出真品，老朝奉陣營（老朝奉、藥不然、鄭國渠）搗亂；依人數取前幾個，6 人沒有鄭國渠和姬雲浮、7 人沒有姬雲浮。
各角色的能力寫在檔頭和前端的規則說明裡。

- 三回合，每回合 4 件獸首（2 真 2 假）。輪到的人鑑定（方震是查驗一個人的陣營）→ 用技能（老朝奉調換、藥不然偷襲、鄭國渠封鎖）→ 指定下一位還沒行動的人。
  第一回合隨機一個人先，之後由上一回合最後行動的人開始。行動有時限（預設 60 秒，可以不限），時間到或斷線 10 秒就自動隨機交棒。
- 每個人的鑑定結果只在自己的 view 裡，其他人只看得到「誰在行動」和行動順序；老朝奉和藥不然看得到彼此的身分。
  被老朝奉調換過的結果、所有獸首的真假和每個人用了什麼技能，結束後才公開。
- 討論：線上模式在聊天室打字、有倒數；線下模式當面說，沒有倒數，都按「可以投票了」才往下。
- 投票用籌碼：每人每回合 2 枚，可以留到之後，最後一回合要全部投出；送出後到開票前都還能改。得票第一的入選但不公開真假，第二名入選並公開（同票照生肖順序）。開票後公開每個人怎麼投。
- 三回合後鑑人（許愿陣營找老朝奉、老朝奉找許愿、藥不然找方震，鄭國渠不投），再計分：入選的真品每件 1 分、許愿陣營過半數投中老朝奉 +1、
  許愿沒被找到 +2、方震沒被找到 +1，6 分以上許愿陣營贏；六件入選的全是真品就直接贏、不用鑑人。分數在同一個房間累計（贏的陣營每人 1 分）。
- 電腦玩家：好人照實說出看到的結果、壞人反著說（討論時發在聊天室，也記成結構化的「說法」）；真人在聊天室打「鼠首是真的」「牛 假」這種句子也會被記下來。
  投籌碼相信自己看到的、再參考別人的說法；鑑人時好人找說法和公開結果對不上的人，老朝奉找每回合都報兩件的人，藥不然找從來不報獸首的人。

### 只有一個詞

`/games/justone`：3～10 人的合作派對遊戲（`backend/src/justone.rs`），改編自桌遊 Just One，不能加電腦。每題輪一個人猜，其他人是出題的人。

- 流程：出題的人同時各寫一個提示詞（3 人時每人兩個；不能包含題目、也不能是題目的一部分，送出時就擋下來）→ 自動刪掉一樣的提示 →
  出題的人手動把意思太像的標「太像了」（30 秒，大家都按「檢查好了」就提早結束）→ 猜的人只看到留下來的提示，猜一次或跳過 → 公布。
- 比對都先正規化：去掉空白標點、全形轉半形、英文轉小寫、臺→台。正規化之後一樣的提示全部作廢；猜的答案正規化之後完全一樣才算對，

  （桌遊本來就不能交談），題目和提示不會從聊天室漏給猜的人。

### 大老二

`/games/bigtwo`：4 人的派對遊戲（`backend/src/bigtwo.rs`），人不夠由房主加電腦補到 4 人。每個人的 view 只有自己的手牌，其他人只看得到張數，結束時才公開剩下的牌。

- 台灣常見的玩法：3 最小、2 最大，同點數比花色 ♠ > ♥ > ♦ > ♣。牌型有單張、對子，以及五張牌型：順子 < 同花 < 葫蘆 < 鐵支 < 同花順，同張數才能壓。
  第一局拿到 ♣3 的人先出（第一手要包含 ♣3），之後由上一局的贏家先出。pass 之後這一圈還能再出，其他三家都 pass 就由最後出牌的人重新出。
- 計分：有人出完時，其他人照剩下的張數扣分，10 張以上加倍、13 張三倍，贏的人拿走全部扣分；分數在同一個房間累計。
- 房主的選項（括號是預設）：同花算不算牌型（算）、鐵支和同花順能不能壓單張和對子（不能）、三條（不能出）、
  順子大小（2 最大：34567 最小…10JQKA < A2345 < 23456；或 A 當 1：A2345 最小）、結算時手上每張 2 再加倍（不加倍）、每手思考時間（30 秒，可以不限）。
  JQKA2 這種繞過 2 的不算順子。
- 時間到或斷線（等 5 秒）會自動處理：能 pass 就 pass，自由出牌就出最小的單張。
- 輪到自己時 view 會附上所有能出的組合，「提示」就在裡面輪流切換，選的牌是不是能出也靠這份清單判斷，前端不用重寫一次規則。
- 電腦玩家先把手牌拆成「出最少次就能出完」的組合（對自己手牌的每個子集合做動態規劃），再用代價挑要出哪一手：保留對子和五張牌型、
  2 和 A 留到要搶出牌權或擋人時才用、有人只剩一兩張時優先擋。每手想 0.8～1.5 秒。

### UNO

`/games/uno`：2～10 人的派對遊戲（`backend/src/uno.rs`），可以加電腦補位（最多 9 個）。每個人的 view 只有自己的手牌，其他人只看得到張數，結束時才公開剩下的牌。

- 標準 108 張：四色各有 0 一張、1～9／跳過／迴轉／+2 各兩張，加上萬用、萬用+4 各四張。每人 7 張，起始牌一定是數字牌（翻到功能牌就塞回牌堆底）。
  出同顏色或同數字／符號的牌，萬用牌隨時能出、出的人指定顏色（萬用+4 沒有「質疑」規則，隨時能出）。兩個人玩時迴轉等於跳過。
- 沒得出或不想出就抽牌，抽到能出的那張可以馬上出、也可以不出；抽牌堆抽完就把棄牌堆洗一洗再用。第一局隨機一個人先出，之後由上一局贏家的下一位先出。
- UNO：出到剩一張時要喊（出牌前先按「UNO!」跟著出牌一起送，或出完馬上補按）。沒喊的話在下一個人動作前，其他人都能按「抓」，被抓到罰抽 2 張；
  誰先送到伺服器算誰，下一位一出手就來不及了。抽了牌就不算喊過，下次剩一張要重喊。
- 房主的選項（括號是預設）：+2／+4 疊加（不能疊；開了之後 +2 上可以疊 +2 或 +4、+4 上只能疊 +4，不疊就把累積的全抽走）、
  沒得出時抽一張或抽到能出為止（抽一張）、每手思考時間（20 秒，可以不限）、計分方式（單局：贏的人 +1 分；或累計點數：
  贏的人拿其他人手上牌的點數，數字照面額、功能牌 20、萬用牌 50，先到 200／300／500 分的人拿下整場，下一局重新算）。
- 時間到自動抽牌、不出；斷線的人等 5 秒由電腦代打（代打一定會喊 UNO）。
- 電腦玩家：出自己最多的顏色、順便先丟點數高的牌，萬用牌留到沒別的能出或快出完時才用，下一家剩一兩張時用跳過、+2、萬用+4 卡他；
  被 +2 時能疊就疊。萬用牌指定手上最多的顏色。喊 UNO 偶爾會忘（約 15%），看到別人沒喊大約六成會在 1～3 秒內抓。每手想 0.9～1.6 秒。

### 德州撲克

`/games/poker`：2～9 人的無限注德州撲克（`backend/src/poker.rs`），人不夠由房主加電腦補位。**只用遊戲籌碼**，不能儲值也不能換錢。
一局是一整場牌局：一手接一手自動打下去，只剩一個人有籌碼（或打滿手數上限，籌碼最多的人贏）就結束，房主也可以隨時「結束牌局」回到大廳。輸光的人留在桌邊觀戰。

- 規則：每手按鈕往左移，按鈕左邊小盲、再左邊大盲；單挑時按鈕下小盲、翻牌前先行動，翻牌後換大盲先。翻牌前、翻牌、轉牌、河牌四輪下注。
  最少下注一個大盲，加注至少要加到上一次完整加注的幅度；全下不足一次完整加注時，已經行動過的人只能跟或棄（累積起來夠一次完整加注才重新開放）。
  大盲籌碼不夠時照一個大盲算要跟的額度。
- 底池：每手記每個人投入的總額，一輪結束（和一手結束）時沒人跟的部分退回；攤牌時照「還沒棄牌的人投入的額度」一層一層切成主池和邊池（`side_pots`），
  每個池各自比牌，平手平分，除不盡的籌碼從按鈕左邊開始一人一枚。
- 牌力（`evaluate`）：直接從點數張數和花色位元算 7 張裡最好的 5 張，編成一個整數（牌型 + 五個踢腳），比大小就是比整數；A2345 是最小的順子。
  攤牌時另外列出組成最好牌型的 5 張，前端在公牌上標出來。
- 只有自己的 view 有自己的底牌。攤牌只公開必須亮的牌：沒人能再下注的全下大家都亮；否則贏家和河牌被跟注的人亮，其他人蓋牌，棄牌的牌永遠不公開。
  一手結束後可以自己按「亮牌」。view 附上自己目前的牌型（「目前：兩對」）和這幾手的行動紀錄。
- 房主的選項（括號是預設）：起始籌碼（1000，至少 10 個大盲）、盲注（10／20）、每幾手升一次盲（10 手，可以不升）、手數上限（不限）、每次行動的思考時間（30 秒，可以不限）。
  時間到或斷線（等 5 秒）會自動過牌，不能過牌就棄牌。全下之後公牌每隔 1.4 秒發一條街，一手結束停 3 秒（有攤牌停 6 秒）再發下一手。
- 電腦玩家只看得到自己的牌和公開資訊：翻牌後用蒙地卡羅模擬（300 次，隨機發剩下的牌給還沒棄牌的對手、補滿公牌）估勝率，
  翻牌前再和起手牌分數（Chen 公式）平均。勝率比「公平分到的份」高很多就加注（底池的五成到一池），夠付底池賠率就跟，偶爾詐唬；每次想 0.8～1.8 秒。

- 遊戲用的詞庫放在記憶體（內建的接上通過的投稿），伺服器啟動時讀一次，之後改到通過的詞就整份換掉；進行中的那一局不受影響，下一局才用新的。
- API：`GET/POST /api/games/draw/words`（自己的投稿／投稿）、`DELETE /api/games/draw/words/{id}`（收回）；
  `GET /api/admin/draw-words`、`PUT /api/admin/draw-words/status`（`{ ids, status: approved|rejected }`）、`PATCH/DELETE /api/admin/draw-words/{id}`。

### 狼人殺

`/games/werewolf`：6～12 人的身分推理派對遊戲（`backend/src/werewolf.rs`），可以加電腦補位（最多 11 個）。角色用民間通用的狼人、平民、預言家、女巫、獵人，守衛可選；
角色說明、介面文字、配色和背景音樂都是自己寫的。

- 配置：依人數有預設（`Lineup::preset`）：6 人 2 狼 2 民＋預言家、女巫；7、8 人再加獵人；9、10 人 3 狼；11 人再加守衛；12 人 4 狼 4 民＋四個神職。
  房主也可以自訂狼人數（1～5）和要哪些神職，其他位子補平民。狼人一定要比好人少；屠邊時至少要有 1 個平民和 1 個神職（不然一開局就分出勝負），配不出來不能開始
  （`Options::lineup`，前端 `types.ts` 的 `lineupOf` 照抄一份給大廳顯示）。
- 流程：看身分（狼人互相認識）→ 夜晚 → 女巫 → 天亮公布出局的人 → 出局的人確認技能 → 遺言 → 討論 → 投票放逐 → 被放逐的人確認技能 → 遺言 → 天黑。
  - 夜晚守衛、狼人、預言家同時行動（彼此不影響，同時做比較快）：守衛守一個人（可以守自己、可以空守，不能連兩晚守同一人）；
    狼人在狼人頻道商量、各自投票（可以空刀），全部投同一個人就定案，時間到照多數，平手隨機，沒人投就隨機選一個好人；預言家查驗一個人是不是狼人（同一人不能查兩次）。三種人都做完就提早結束。
  - 女巫：解藥救今晚被刀的人，或用毒藥毒一個人，同一晚只能用一瓶；解藥用掉之後就看不到刀口。能不能救自己是選項（不行／只有第一晚〔預設〕／可以）。
  - 天亮結算：被刀的人被守衛守護或被女巫救就沒事，但同守同救還是出局；守衛擋不住毒藥。只公布誰出局，不說原因。
  - 獵人被刀、被放逐時可以開槍帶走一個人，被毒倒不能開槍；開槍時公開他是獵人。
  - 遺言（選項）：沒有／第一晚出局和白天出局的人才有〔預設〕／都有。線上在聊天室說（輪到他時，他說的話大家都看得到），線下當面說；本人按「說完了」換下一位。
  - 討論：線上在聊天室，有倒數（2～8 分鐘），活著的人都按「可以投票了」就提早投票；線下當面說，房主按「開始投票」，倒數（當上限用）到了也會開始。
  - 投票放逐：投一個還活著的人或棄票，開票前能改，開票後公開誰投誰。平票（選項）：平票以外的人在平票的人之間再投一次，再平就沒人出局〔預設〕；或直接沒人出局。
  - 勝負：狼人全部出局好人贏；屠邊〔預設〕是平民或神職其中一邊全部出局狼人贏，屠城是好人全部出局狼人贏。同時發生時好人贏（狼人已經全滅）。
    打到第 20 天還沒分出勝負算狼人贏（一直空刀、一直平票才會發生）。贏的陣營每人 1 分，在同一個房間累計。
- 隱藏資訊：身分只在自己的 view 裡（狼人看得到隊友；開過槍的獵人公開；選項「出局時公開身分」打開時出局的人也公開）。
  狼人的票和刀口只給狼人，刀口另外給還有解藥的女巫；查驗結果只給預言家；守衛、女巫的紀錄只給自己。對局中死因不公開，結束後才公開所有身分和每一晚的守護、刀口、用藥、查驗。
  - 有獵人的局，出局的**每個人**都要確認技能（不是獵人的按「確定」）；女巫出局或沒藥時，女巫這一步照樣等 4～8 秒。這樣別人才看不出誰是獵人、女巫還在不在。
  - 夜晚沒有行動的人可以點一個人記下「懷疑」（只有自己看得到）。線下大家同時在點手機，旁邊的人看不出誰有夜間行動。身分卡可以點一下遮住。
- 聊天：夜晚只有活著的狼人之間看得到（狼人頻道），其他人夜晚說的話不送出。出局的人只能和出局、觀戰的人聊；剛出局、技能或遺言還沒處理完的人不能聊，
  免得從觀戰的人那裡聽到什麼，再用遺言或開槍帶回場上。觀戰的人看不到任何身分和夜晚的結果（跟活著的平民知道的一樣多），說的話也只有出局、觀戰的人看得到，
  所以聊天室兩頭都漏不出東西給場上的人。
- 線下模式：網頁當法官，夜晚各自在手機上行動（狼人用狼人頻道商量），白天當面討論，投票一樣在手機上。
  伺服器不知道誰是房主，「開始投票」「下一位遺言」的按鈕只給房主看到（房主沒有座位時所有人都看得到），和傳話畫畫的「下一步」一樣。
- 時限和斷線：看身分 15 秒、夜晚 20～120 秒（預設 45）、女巫 25 秒、天亮 6 秒、確認技能 20 秒、遺言每人 45 秒（線下 60）、討論、投票 40 秒（重投 30）、公布票數 6 秒。
  時間到：守衛空守、預言家不查、狼人照多數或隨機、女巫不用藥、獵人不開槍、沒投的算棄票、遺言換下一位。斷線的人在一個階段裡等 10 秒就不等他，
  其他人都做完就直接往下（狼人只剩斷線的就照上面的規則選）。
- 電腦玩家只知道自己的身分和公開的資訊（狼人知道隊友）。真人和電腦說的話都會記成結構化的「說法」：自稱身分（「我是預言家」）、說某人是狼（「3號是狼」「查殺小明」「投小明」）
  或是好人（「小明金水」「小明不是狼」），名字和「N號」都認得。電腦照這些說法算每個人有多可疑：只有一個人跳預言家就相信他的查驗，兩個人對跳就各信一半，
  夜裡出局的預言家比較可信；自己是真的預言家就知道其他跳預言家的是假的。
  - 預言家查最可疑的人，白天報查驗結果；守衛守唯一跳預言家的人，不然守自己或看起來是好人的人；女巫第一晚多半會救，確定誰是狼人（例如被唯一的預言家查殺）才用毒；獵人夠可疑才開槍。
  - 狼人跟著真人隊友的刀（真人改票時電腦隊友一兩秒內跟上），自己挑時先刀跳預言家、女巫、守衛的人，避開跳出來的獵人；大約三分之一的局會派一個狼人電腦假跳預言家
    （有人跳就對跳查殺他，偶爾給隊友金水）。投票投最可疑的人（狼人不投隊友，想推掉跳預言家的人）。
  - 電腦在討論時說一句話，遺言時報自己的身分和資訊，夜裡也會在狼人頻道說「刀 X 吧」。

### 跳棋

`/games/chinesecheckers`：2～6 人的六角星跳棋（`backend/src/chinesecheckers.rs`），可以加電腦補位（最多 5 個）。沒有隱藏資訊，
但人數會超過兩個人，所以不用棋類的轉送房間，改用派對房間、規則在伺服器驗證。每個人的 view 都一樣（整個盤面），只差 `you`。

- 棋盤 121 格：中間 61 格的六邊形加上六個 10 格的角。每人 10 顆棋從一個角出發，目標是正對面的角。
  用哪幾個角看人數：2 人對角、3 人隔一個角（目標都是空的角）、4 人兩組對角、5 人空一個角、6 人全部；輪流的順序就是繞著棋盤的順序。
  第一局隨機一個人先走，之後由上一局先走的人的下一位先走（輪流當先手）。
- 走法：走到相鄰的空格；或跳過相鄰的一顆棋（誰的都可以，不會被吃掉）落到正後方的空格，可以連續跳、中途想停就停。
  走一步之後不能再跳，同一手不能經過同一格兩次（起點在這一手裡算空的，也不能跳回來）。不能不走；沒有棋能走時自動跳過（算一手）。
- 長跳（房主的選項，預設關）：對稱跳，同一直線上隔著空格的棋也能跳，棋前後的空格要一樣多，例如隔兩個空格的那顆棋，跳過去落在它後面第三格。
- 防堵：常見的做法有「強制離開出發的角」「可以和堵在目標裡的棋交換」「目標填滿就算贏」，這裡用最後一種，
  因為只看盤面、規則最好講：**目標的 10 格都有棋、而且其中至少一顆是自己的，就算走完；別人的棋要等它的主人走滿 30 手（或已經走完）才算你的**。
  4 人、6 人時你的目標就是對面的家，開局時對方還沒來得及搬家不能算（不然開長跳的 6 人局，電腦互打第 10 手左右就有人「走完」），
  正常一局 30 手前早就搬走了，之後還賴在你目標裡的棋等於替你填格子，堵人只會讓對方更快走完。
  別人的一手剛好讓你的目標符合條件也算你走完（走的人先算名次）。
- 結束：第一個人走完就結束，其他人照進度排名；房主可以選「排出所有名次」，走完的人之後輪到時跳過，剩一個人時結束。
  排名次時走完的人的棋會拿下棋盤：它們不會再動，留著可能把別人最後一顆棋永遠困在角落的尖端（電腦互打時真的發生過），畫面上照樣顯示走完時目標裡有幾顆。
  每局第一名 +1，在同一個房間累計。
- 防拖延：每人最多走 150 手（電腦互打第一名大約 30～50 手、開長跳 20～30 手，排完所有名次最多 60 手左右），大家都走滿還沒分出勝負就照進度排名：
  每顆棋到目標尖端的距離加總（走完時是 20、剛開始是 140）越小越前面，一樣的話看目標裡有幾顆自己的棋。
  加上每手的時限，來回走也拖不了太久。
- 每手思考時間（不限／15／30／60／120 秒，預設 30）。時間到由電腦代走這一手；斷線的人等 5 秒由電腦代走，重新連上就自己走。
- 動作只有一種：`{ type: 'move', path }`，`path` 是經過的格子（含起點）。格子編號照立方座標一列一列排（0 是最上面的尖端、60 是正中央），
  前端 `frontend/src/games/chinesecheckers/board.ts` 用一模一樣的規則算出每顆棋能到的格子和連跳的路徑，點目的地就把整條路徑送出去，伺服器再驗證一次。
  view 的盤面是 121 個字的字串（`.` 是空格、數字是座位），另外有上一手的路徑和這局一共走了幾手（`moveNo`，前端靠它播移動的動畫）。
- 畫面：棋盤轉成自己的出發角在最下面（觀戰的人看座位 0 的方向），自己的目標用虛線框起來；點自己的棋標出所有能到的格子，
  滑鼠移到目的地上會畫出連跳的路線。點的位置換算成離最近的那一格（兩格中間也算），360px 寬的手機上也點得準。
  上一手畫出整條路線、起點畫虛線圈，棋子會沿著路線跳過去（系統設定減少動態時不播）。
- 顏色：六個座位是紅、藍、綠、黃、黑、白，CSS 變數 `--cc-red`…`--cc-white` 和棋盤的 `--cc-board`、`--cc-hole` 在 `index.css`，亮色深色各一組（深色主題的黑棋有淺色的邊）。
- 電腦玩家：每顆棋到目標尖端的距離 d，代價是 Σ(d + 0.08·d²)，平方項讓落後的棋比較急著走；挑代價降最多的那一手，
  前 6 名再往下看自己的下一手（能不能接著跳得更遠），最近離開的 6 個格子不走回去免得來回晃，能直接走完就走完。每手想 0.7～1.4 秒。
  2～6 個電腦互打（含長跳、排出所有名次）都能在 120 手內走完，`cargo test` 裡會跑；
  `cargo test --lib game_lengths -- --ignored --nocapture` 印出各種人數平均要走幾手，調整電腦或規則時看這個。

### 暗號接頭

`/games/contact`：4～10 人分成兩隊的派對猜詞遊戲（`backend/src/contact.rs`），不能加電腦。規則細節、隊名、介面、配色和音樂都是自己的。

- 選隊：開局先進「選隊」，每個人自己點加入「翡翠」或「紫晶」、要不要當聯絡人（每隊一位，其他人是組員）；房主可以「隨機分隊」（兩隊最多差一人，聯絡人照輪替），再按「開始發牌」。
  還沒選隊的人補進人少的那隊，沒有聯絡人的隊照輪替挑一位（在線的、當過最少次、最久沒當的優先），每隊至少 2 人。
  下一局沿用上一局的分隊（新來的人補進人少的那隊），聯絡人自動換人，大家還可以再改。
  「隨機分隊」「開始發牌」伺服器不檢查是不是房主（遊戲不知道誰是房主），按鈕只出現在房主的畫面上；房主沒有座位時座位上的人都看得到（同傳話畫畫的「下一步」）。
- 盤面：5×5 共 25 個詞，密碼表是先手隊（隨機）9 張、後手隊 8 張、路人 7 張、叛徒 1 張。
- 流程：輪到的隊伍，聯絡人給「一個詞＋一個數字（1～9）」→ 組員在格子上標記想翻的（同隊的人看得到），任一組員按「翻開」。
  這輪最多翻「數字＋1」張：翻到自己人可以繼續，翻到路人或對方的就換隊，翻到叛徒立刻輸；翻過一張之後可以「結束這輪」。
  先翻完自己隊所有詞的隊伍獲勝（被對方翻到也算）。翻開時帶著「已經翻開幾張」，兩個組員同時按也只會翻到一張。
- 提示詞和只有一個詞一樣先正規化（去掉空白標點、全形轉半形、英文轉小寫、臺→台）再比：不能是盤面上的詞（翻開的也算），
  也不能包含盤面上的詞或被盤面上的詞包含，送出時就擋下來，並告訴聯絡人撞到哪個詞；只能是一個詞，不能有空白。
- 選項：給提示和猜的時間（1／2／3 分鐘或不限）、線下模式（聯絡人當面說出提示，網頁上只選數字，負責顯示盤面和翻牌；
  聯絡人在自己的手機上看密碼表，可以按「遮住密碼表」防偷看）。
- 時限和斷線：給提示時間到就跳過這輪，猜的時間到就換隊。輪到給提示時聯絡人斷線，同隊還有看過密碼表的人在線就直接由他給；
  沒有就等 20 秒，隨機請一位在線的組員接手（他看到了密碼表，這局就不能再標記、翻牌）並重新計時；整隊都不在就跳過這輪。
  猜的時候這隊的組員都斷線 15 秒就換隊。原本的聯絡人回來後還是看得到密碼表、也能給提示，但不能翻牌。
- 隱藏資訊：密碼表只在看過密碼表的人（兩位聯絡人和中途接手的人）的 view 裡，結束後才公開給所有人；觀戰的人也看不到，
  因為猜的人開個新分頁進來觀戰就能偷看。對局中看過密碼表的人在聊天室說的話只有看過密碼表的人看得到（不能偷偷提示隊友），
  組員的標記只送給同一隊。
- 同一個房間記每個人贏了幾局、當過幾次聯絡人；下一局盡量不出現用過的詞，同一個盤面不會有互相包含的詞（例如「斑馬」和「斑馬線」）。
- 詞庫在 `backend/src/contact_words.txt`（860 多個 2～4 個字的名詞，挑容易聯想、有好幾種意思的）。
- 兩隊、路人、叛徒的顏色是 `index.css` 的 `--ct-jade`、`--ct-amethyst`、`--ct-bystander`、`--ct-traitor`（翻開後卡面上的字是 `--ct-ink`），
  亮色深色各一組；格子另外標 ◆ ▲ ○ ✕，分不出顏色也看得懂。格子的字照盤面寬度（`cqi`）和字數縮放，360px 寬的手機上四個字也放得下。

### 吹牛骰子

`/games/liarsdice`：2～10 人的派對遊戲（`backend/src/liarsdice.rs`），可以加電腦補位（最多 9 個）。每人一個骰盅、5 顆骰子，只看得到自己的。
一「輪」是大家一起搖、輪流喊到有人開為止；一「局」是一整場（結算後房主按「再來一局」開下一局）。

- 規則：從起叫的人開始輪流喊「N 個 F」（場上至少有 N 顆 F 點），下一個人要喊得更大（個數更多，或個數一樣、點數更大），或者「開」。
  開了就全部掀開來數：符合的有 N 個以上是喊的成立、開的人輸，不夠就是喊的人輸。個數最多喊到場上的骰子總數，喊到頂了下一個人只能開。
  第一輪隨機一個人先喊，之後由上一輪輸的人先喊（他出局了就換下一位）。
- 房主的選項（括號是預設）：
  - 一點萬用（開）：數的時候一點也算進去（喊的就是一點時只數一點），所以一點最大：2 < 3 < 4 < 5 < 6 < 1。關掉的話一點只算一點，點數照數字比。
  - 有人喊過一點之後，這輪一點不再萬用（開，一點萬用時才有）。
  - 起叫最少個數（人數 + 1；也可以選人數、不限）：人數是還沒出局的人，而且不超過場上骰子總數的一半（無條件進位），淘汰到骰子很少時起叫的人才不會一開口就輸。
  - 散骰重搖（開）：五顆點數全不同，在這輪自己還沒喊、沒開之前可以按「重搖」（可以一直搖到不是散骰），紀錄裡會寫他重搖了；不滿五顆不算散骰。
  - 勝負（淘汰制）：淘汰制是輸的人少一顆骰子，骰子輸光就出局，剩最後一個人贏；計分制打固定輪數（5／10／15／20 輪，預設 10），
    每個人一直都是 5 顆，輸一次喝一杯，最後喝最少的贏（同杯數一起贏）。
  - 每手思考時間（30 秒，可以不限）：時間到或斷線（等 5 秒）由電腦代為出手（照機率喊或開，不唬人）。
- 揭曉：開了之後所有人的骰子攤開 9 秒（場上的真人都按「下一輪」就提早結束）：符合的骰子框起來、萬用的一點用虛線框、不算的變淡，
  底下列出「F × 幾顆 ＋ 萬用的 1 × 幾顆 ＝ 共幾個」、誰輸、為什麼輸。搖骰時骰盅會晃、搖完骰子滾出來，揭曉時一顆一顆翻開。
- 分數：兩種模式都記杯數（輸一次一杯），房間跨局累計每個人贏了幾局、喝了幾杯。
- 隱藏資訊：骰子在揭曉前只在自己的 view 裡，觀戰和出局的人也看不到別人的骰子（不然開第二個分頁當觀戰就能偷看），所以聊天不用另外擋。
  揭曉時 view 放的是開的那一刻所有人的骰子，下一輪開始搖就拿掉。
- 電腦玩家只知道自己的骰子、每個人剩幾顆和這輪喊過的：用二項分布算「這個喊價成立的機率」（自己的骰子是確定的，其他人每顆 1/6，一點萬用時 1/3），
  別人這輪喊過的點數就當他手上大概多幾顆。輪到時比較「開」贏的機率和「往上喊」有多安全，太不可能就直接開，偶爾故意喊自己沒有的點數虛張聲勢。
  四種個性照加入順序輪：穩健阿伯（幾乎不唬人）、唬爛王（常唬人，也不太相信別人）、算盤阿姨（照機率、偶爾唬一下，最難纏）、老實阿弟（很相信別人喊的，不太開）。
  拿到散骰時手上沒有萬用的一點才重搖（有的話每個點數都有兩顆，留著比較好）。每手想 1～2.2 秒，開的時候偶爾在聊天室說一句。
  調整參數時用 `cargo test --lib liarsdice::tests::bot_stats -- --ignored --nocapture` 看每種個性對「只會往上喊、從不開」的人的勝率（目前 9 成以上），
  以及四種同桌時的勝場和開對的比例（目前開對 7 成左右）。
- 喊價介面：點數是六顆骰子的按鈕（底下寫最少要喊幾個），個數用加減，旁邊寫「最低能喊」；自己手上符合的骰子會框起來，也寫出其他人平均大概有幾個。
- 背景音樂是另外寫的一段熱鬧的酒館小曲（`frontend/src/games/liarsdice/song.ts`），不是任何現成的曲子。

### 3D 賽車

`/games/racing`：3D 賽車（`frontend/src/games/racing/`），用 three.js 畫。單人和電腦比全部在瀏覽器裡跑；
多人連線是派對遊戲（`backend/src/racing.rs`，id `racing`），見下面的「多人連線」。

- 整個畫面都是遊戲：`games/registry.ts` 裡設了 `fullscreen` 的遊戲，`GamePage` 不放標題列，遊戲自己用 `position: fixed` 蓋住頁首和側邊欄，離開的按鈕放在遊戲畫面上。
  按「開始比賽」時再請瀏覽器切成全螢幕（選單裡可以關掉；iPhone 的 Safari 不支援，只會蓋滿網頁）。
- 四條賽道（`tracks.ts`）：控制點連成封閉的 Catmull-Rom 曲線，每 2 公尺取一個點（`track.ts`）；路面、路緣石、護欄、地形、樹和大樓都從這些點長出來（`world.ts`），貼圖用 canvas 畫，不下載圖檔。
  長直線兩頭各要有兩個控制點在同一直線上，不然曲線會在直線中間往外彎（信義的路口前後各放 24、48 公尺兩個點）。
  路面的虛線和接縫、路肩的深淺橫條、護欄每 2.5 公尺的立柱（夜城是一段一段的燈條）都是為了開快時看得出景物往後衝，改貼圖時別把它們拿掉。
- 起伏和變化：控制點的高度決定上下坡，`bank` 是彎道最多傾斜幾度（照彎度自動算，越急越斜、外側高，沿著賽道抹平），`bumps` 是路面上的小隆起（餘弦形狀，開快會飛起來）。
  `profile` 是照距離排的高度（[離起跑線幾公尺, 高度]，兩點之間用餘弦接起來，每一點都是坡頂、坡底或平台），有寫就不用控制點的高度：信義的路口位置照真實地圖不能動，高低另外排。
  - 起伏很大（最陡的地方坡度四成多）：海岸從海邊爬上 85 公尺的山頂、彎道傾斜 8 度、中段兩個鼓包；峽谷從谷底爬上 115 公尺的台地再衝下來，台地邊緣會飛；
    夜城是 8 字形，過了起跑直線就爬上高架，南北向那段從起跑直線上方 40 公尺飛過去再俯衝下來（半路有鼓包）；信義見下面。
  - 追車鏡頭跟著坡度俯仰（騰空時跟著車子往上、往下的方向），陡坡上車子和前面的路都在畫面裡；鏡頭也不會低過它底下的路面（下坡時車子後面的路比車子高）。
  - 電腦的建議速度也看坡：下坡煞車距離比較長（重力往前推），過坡頂最多開到「騰空門檻」的 1.6 倍（`AI_AIR`），還是會飛，但不會飛到落地時正好撞牆。
  - 橋是自動找的（`track.ts` 的 `bridge`）：從另一段路上方 4 公尺以上跨過去的地方（前後多包一段），或路面比賽道自己的地形高出 1.5 公尺以上（夜城的地面是平的，整段高架都是橋）。
    地形不貼著橋（`nearest(x, z, true)` 跳過橋），改畫橋面板和橋墩（`world.ts` 的 `addBridges`），橋墩不會立在底下那條路上，橋下也不放路燈和擺設。
  - 路面高度用坡度做三次內插（坡度連續），過坡頂才不會一格一格地抖。地形格子約 7 公尺一格，靠路的地方比路面低 0.55 公尺，護欄往下畫 1 公尺蓋住縫；
    改了賽道可以照 `world.ts` 的算法建高度格子，檢查地形有沒有穿出路面（凹下去的地方最容易穿）。
  - 賽道上下交叉時，找車子位置只在上一次的附近找，不會跳到另一層；上下差 2.2 公尺以上的車撞不到。
- 「台北信義」是照 OpenStreetMap 做的真實街道：市府路 → 松壽路 → 松仁路 → 松廉路 → 松智路 → 信義路，繞著 101，一圈 1574 公尺。
  - 地面是平的（信義計畫區本來就平），賽道自己衝上 14～38 公尺的高架再俯衝下來（`tracks.ts` 的 `profile`）：轉角都在高架上，松壽路中間的大坡頂、松廉路往 101 衝的那段開快會飛很遠。
    三座人行空橋跨過賽道（市府路兩座、松壽路一座），那三個地方要貼著地面，改 `profile` 時別讓高架撞到空橋。
  - 資料由 `frontend/scripts/osm-xinyi.mjs` 離線產生成 `games/racing/osm/xinyi.json`（約 165 KB，gzip 後約 65 KB），跟著賽車的程式一起打包，遊戲裡不會去打 OSM。
    要更新地圖時手動跑 `node scripts/osm-xinyi.mjs --refresh`（重新向 Overpass 下載；不加 `--refresh` 就用 `node_modules/.cache/osm-xinyi.json` 的快取，`--verbose` 會列出因為太靠近賽道被拿掉的建築）。
  - 賽道的控制點是腳本找出來的路口（兩條路共用的節點取平均），彎道在路口前後切角；周圍 650 公尺內的建築、街道、綠地、行道樹都帶，60 公尺以上的高樓 1.5 公里內都帶（天際線）。
  - 建築高度用 `height`，沒有就用 `building:levels` × 3.3 公尺，兩個都沒有（約四成）照面積和 OSM id 估樓層（每次產生都一樣）。有 `building:part` 的建築只畫 part（101 的塔身、觀景台、塔尖都是 part，有 `min_height`）；
    地下的車站、室內的房間不畫；離賽道中心線不到「護欄 + 1.5 公尺」的建築拿掉（路燈立在護欄外 1.2 公尺）。
  - `city.ts` 把輪廓往上長成大樓（50 公尺以上是玻璃帷幕、矮的是貼磁磚的公寓），街道和綠地鋪在地面，大馬路兩旁每 12 公尺種一棵行道樹。
    外牆有五種：玻璃大樓是藍灰色、綠色帶窗、銀色格子框，公寓是磁磚和裝了鐵窗、掛著冷氣機的老公寓。離賽道 380 公尺內的建築屋頂有東西：
    公寓的不鏽鋼水塔、頂樓加蓋的鐵皮屋（水塔常常放在鐵皮屋上面），大樓頂上往內縮一圈的機房和設備，110 公尺以上有避雷針和紅燈。
  - 一看就知道是信義區的東西在 `landmarks.ts`：
    - 台北 101：OSM 只有一疊方塊，換成照真實比例做的（往上收的基座、四面的大古錢、八節往外開的竹節、頂樓、塔尖）。方向和大小從 OSM 塔身的輪廓量，塔身附近 100 公尺以上的 part 都不畫。
      每節頂端有燈條，顏色照星期幾換（和 101 晚上的燈一樣：週一紅、週二橙、週三黃、週四綠、週五藍、週六靛、週日紫）。
    - 人行空橋（OSM 的 `highway=footway` + `bridge=yes` + `layer≥1`）：二樓高的玻璃走廊和柱子，柱子不立在賽道上，底下不放路燈和行道樹。
    - 每個彎前 40 公尺掛綠底白字的路名牌（轉進去的那條路，中英文和箭頭；英文用 OSM 的 `name:en` 縮寫成路牌的寫法）。
    - 東南邊的四獸山、南港山：腳本從 AWS 上的 Terrain Tiles（terrarium 編碼的 PNG，自己解）取高度，50 公尺一格、一格 2 公尺存成 base64。
      平地的高度會混到建築，所以 3×3 平均不到 35 公尺的地方壓成 0，靠範圍邊緣的慢慢降下來。山在一到五公里外，場景的霧 1.6 公里就全白了，
      所以山不吃霧，顏色直接算好（森林的綠、照到夕陽的那面偏暖、越遠越霧）；鏡頭的最遠距離拉到 6 公里。
  - 地圖資料 © OpenStreetMap 貢獻者，以 [ODbL](https://opendatacommons.org/licenses/odbl/) 授權；選賽道的地方有標出處，`xinyi.json` 是衍生資料庫，同樣以 ODbL 提供。
    地形高度（SRTM）在平地上下亂跳二、三十公尺（把大樓也算進去了），不能拿來做路面高度，只用在遠景的山。
- 物理是街機式的（`physics.ts`）：只有前進和側滑兩個分量，轉彎半徑受側向加速度限制，速度快就轉不過去，要先煞車。
  上坡減速、下坡加速（真的重力沿車頭方向的分量），往彎內傾斜的彎道可以壓得更快（重力 × 坡度 × `BANK_GRIP` 倍）。
  路面往下彎的向心加速度（速度² × 往下的彎度）超過 15 m/s² 就飛起來：在空中照 15 m/s² 落下，不能加速、方向盤只剩三成，落地時畫面震動、揚起塵土、「咚」一聲，重重落地會掉一點速度。
  線上別人的車不送高度，每個人照同一套物理自己算，過坡頂一樣會飛。
- 五種車（`spec.ts` 的 `CARS`）：綜合、極速、加速、操控、甩尾，各自的極速、起步加速、側向加速度（過彎）、甩尾加速的秒數和集氣速度、重量和車身大小都不同，
  外型也不一樣（`car.ts` 的 `SHAPES`：極速是又長又低的楔形車，加速是短短高高的掀背車，操控是小小的單座賽車，甩尾有高高的大尾翼）。
  車撞車時照重量分推開的距離和速度變化，重的車撞輕的車，輕的被撞飛得多。選單上的評分（1～5）是照數值估的，改了數值記得一起改。
  電腦開車的建議速度是照綜合型算的，換成別的車時照側向加速度的平方根調整、極速照自己的車限。
  用模擬（電腦駕駛、不甩尾）比較，四條賽道的單圈時間差不到 4%：海岸環線極速型最快，峽谷、夜城和信義是操控型和加速型最快；甩尾型要玩家自己甩尾才補得回來。
  甩尾像跑跑卡丁車：點一下是小甩（車身斜約 10 度），按住越久車尾甩越開（約 1.4 秒到 40 度）、彎也轉得越急；甩到該有的角度靠「調抓地力」做到（穩定時 tan(滑行角) = 車身轉速 ÷ 抓地力），角度不夠時車身多轉一點讓車尾馬上甩出去。
  放開後 0.45 秒內側滑的速度大多轉回前進方向，車身順順回正、不會一放開就掉速，再照甩尾的時間加速 0.8 或 1.6 秒。參數在 `physics.ts` 開頭的 `DRIFT_*`。
- 電腦對手（`ai.ts`）沿著預先算好的行車線開（把中心線像橡皮筋一樣拉緊），照彎道算出的建議速度踩油門、煞車，前面有車會從旁邊超；難度決定動力和過彎速度，離玩家太遠會稍微放慢或加快。
  調參數時可以用 rolldown 把 `tracks.ts`、`track.ts`、`physics.ts`、`ai.ts` 打包成 node 跑得動的檔案，不開畫面直接模擬整場，看每台車的圈速和撞牆次數。
- 操作：鍵盤（方向鍵／WASD、空白鍵或 Shift 甩尾、C 換視角、R 回到賽道、P 暫停、M 音效、B 音樂）、手機觸控（左下拖曳轉彎，右下油門、煞車、甩尾，可以自動踩油門）、遊戲手把（標準配置）。
- 引擎、風切聲（時速 60 以上越快越大聲）、輪胎、撞擊和提示音都是 Web Audio 即時合成的。設定（含選的車）、音效和音樂開關、每條賽道的最快圈和各圈數的最佳紀錄存在瀏覽器的 localStorage（`games:racing:*`），不上傳。
  最快紀錄的名字帶版本（`racing:records:v3`），賽道改到舊紀錄不能比的時候換一個版本。
- 背景音樂（`music.ts`）也是即時合成，不下載音檔：每條賽道一首，速度、調性、和弦進行和音色不同（海岸是明亮的大調，峽谷是小調搖滾，夜城是合成器浪潮，信義是傍晚的城市流行），
  鼓、貝斯、和弦、琶音、主旋律五軌，8 小節一輪；主旋律用賽道的種子產生，每次聽到的一樣。
  選單和倒數時只有和弦、琶音和輕輕的貝斯，起跑時整首從頭進來，最後一圈鼓變密、旋律高八度，暫停時變小聲。
  排程是計時器每 40 毫秒看一次，把 0.2 秒內要響的音先排進 AudioContext；切到背景時計時器變慢，漏掉的就跳過。
- 高速效果（`speedfx.ts`、`game.ts` 開頭的常數）：超過極速的 50%（約 105 km/h）開始有白色風線從車頭（保險桿兩角和引擎蓋）冒出來，順著車身兩側和車頂往後流（風線跟著車子走，流到鏡頭前就收掉，車頂視角只畫兩側的），超過 55%（約 115 km/h）畫面左右開始往外糊，
  超過 72%（約 150 km/h）畫面外圍出現往外衝的白色集中線，加速噴火時這三樣都更強。模糊和集中線是先把場景畫到貼圖再處理，都用不到時不做這一步；系統設定了「減少動態效果」就不畫風線和集中線。
  高速時鏡頭不震（試過覺得太晃），只有撞到東西時晃一下。
- 追尾鏡頭：視角從 58 度隨速度加到 74 度，噴射再加 9 度；視角變廣時鏡頭同時往車子推近（推軌變焦），車子在畫面上差不多一樣大，只有四周被拉開，速度感主要來自這裡。
  鏡頭位置有做平滑，平滑會讓鏡頭落後「速度 ÷ 平滑係數」（極速時多 4 公尺，車子變小反而不覺得快），所以照車速往前補回去；加速時鏡頭稍微落後（車子往前竄）、煞車時追上來。
- 胎痕（`skids.ts`）：甩尾或轉太急側滑時，兩個後輪在柏油路面留下黑線（甩尾集氣越多越深，騰空、輪子開出路面時不畫），別人的車也有。
  一條胎痕是一串頭尾相接的四邊形，開始和結束時淡入淡出；胎痕不會慢慢消失，固定 16384 段輪流用，最舊的才被新的蓋掉。
  每個畫面只把新寫的那一段上傳給顯示卡（`addUpdateRange`），全部合成一個網格，一次畫完。
- 賽道旁邊的熱鬧（`scenery.ts`，位置都是照賽道自動找的：離每一段路都夠遠、不在橋下或高架旁、地面和路面差不多高、不壓到建築和水）：
  - 看台：起跑線後面（兩邊都試）一座大的，最急的兩個彎外側各一座小的。屋簷、矮牆、兩側的牆都貼廣告，前面的護欄內側掛布條，屋頂前緣一排旗子，夜裡屋簷下有燈。
  - 觀眾：看台上一排排站好，彎道外側也有站在路邊看的人。全部合成一個 InstancedMesh，動作在 vertex shader 裡算：平常三成的人在跳、揮手，
    鏡頭跟著的那台車開到 20～70 公尺內時幾乎大家都跳起來，看台上大約每 17 秒有一次人浪。上衣顏色每個人不同（instance 顏色只乘在 `aPart` 是 1 的頂點上，臉和褲子不變）。
  - 廣告看板：大約每 170 公尺一面，左右輪流，往開過來的方向轉 35 度。廣告全是虛構的品牌（`ads.ts`），看板一格 2:1、布條一格 8:1，各畫成一張貼圖。
  - 每條賽道自己的點綴（`tracks.ts` 的 `decor`）：海岸有海上的帆船、靠海高地上的燈塔、沙灘傘；峽谷有熱氣球；夜城有從地面往天空掃的探照燈；信義的空橋上站滿往下看的人。
  - 樹、大樓、路燈、行道樹都避開看台和看板佔走的地方（`occupied`）。
- 夜城的大樓（`towers.ts`）：方塊、往上退縮的高樓、裙樓加玻璃塔、圓柱大樓、尖塔頂；外牆有格子窗、橫向帶窗、玻璃帷幕三種，每棟再乘上自己的顏色。
  屋頂有水塔、冷氣機、天線（紅色的航空障礙燈一閃一閃），一部分有霓虹燈邊、轉角的燈條和朝著賽道的招牌。
- 畫面內插（`game.ts` 的 `blendPoses`）：物理固定每秒 120 步，畫面的格數對不上（60 Hz 一格有時 1 步有時 3 步、144 Hz 每 6 格就有一格是 0 步），
  直接畫物理的位置車子會一頓一頓的。所以每一步物理之前記下每台車的位置，畫的時候放在前後兩步之間（車子、鏡頭、特效、小地圖都用這個位置），畫完再換回物理的狀態。
  一步移動超過 5 公尺（放回賽道）就直接畫新的位置。
- 換賽道、換車時先把 shader 編好（`renderer.compile`），包括還沒出現的噴火、和高速模糊要的另一組（畫到貼圖時輸出的色彩空間不同，每個材質都要另一個 shader）：
  不先編的話，第一次開到會模糊的速度（約 115 km/h）時要一口氣編完，畫面會頓一下。
- 一直掉幀時自動降低解析度。

#### 多人連線

選單上方切到「多人連線」，或打開邀請連結（`?room=`）、從遊戲室開：2～8 人同一條賽道，人不夠可以加電腦（見下面的「電腦」）。
房主在大廳選賽道、圈數（1、3、5 圈）、加電腦和電腦難度，起跑位置每局重新抽。

- **選車**：房主按開始後，每個人有 30 秒選車型和顏色（`racing.rs` 的 `SELECT`；view 的 `select` 有剩幾毫秒和每個座位選好了沒有，選完是 null）。
  - 畫面左邊（手機在下面）只有車型和顏色，右邊是 3D 預覽：就是後面的遊戲畫面（`RaceGame.showroom`），選的車停在這局的起跑線上、鏡頭繞著轉，
    `setStage` 把投影中心移到預覽那一塊（`camera.setViewOffset`），車子不會被選單蓋住。單人也一樣，選好賽道後按「下一步：選車」。
  - 換車送 `{type:"pick", car, color}`（color 是 `CAR_COLORS` 的第幾個）：車型隨便選，顏色先選先贏，別的真人選走的會劃掉不能選，伺服器也會擋。
    電腦隨機配一種車，顏色讓給真人：真人選了電腦的顏色，電腦就換一個沒人用的。顏色有 10 種、座位最多 8 個，一定分得到。
  - 按「選好了」送 `{type:"ready"}`，之後這局不能再換；電腦一開始就選好了。連著線的真人都選好了（斷線的不等）或時間到，就照當時選的開始 5 秒倒數。
  - 每局一開始是上一局開的車（跟著人走）；第一局是綜合型和沒人用的第一個顏色，前端再換成自己平常開的（那個顏色被別的真人選走了就等它空出來，自己動手選過就不管）。
    選的車也會記下來給單人用。

- **物理在每個人的瀏覽器裡跑**，伺服器不算物理，也不知道賽道長什麼樣子。
  - 自己的車照單機版操作，每秒送 20 次狀態：`{type:"state", d:[時間, x, z, 車頭方向, vx, vz, 轉向速度, 方向盤, 旗標, 進度]}`，格式在 `online.ts` 的 `encodeState`。
  - 伺服器每 50 毫秒把有更新的車合併成一則 `cars` 事件轉送給所有人，觀戰的人也收得到。
  - 別人的車收到的是一小段時間以前的狀態，用速度和轉向速度往前推算到「現在」才畫（`RemoteDriver`）。
    新狀態進來時和舊的推算差了多少，就當作誤差在零點幾秒內消掉；差超過 8 公尺（重生、卡頓）就直接跳過去。
    3 秒沒收到某台車的狀態（斷線、切到背景）就不畫、不撞。
  - 不把別人的車畫在「收到的那個時間」：極速時 0.1 秒就差了 7 公尺，並排的車看起來會落後一截，撞到的也是它以前的位置。
- **碰撞**：各自的瀏覽器只推開自己的車（`physics.ts` 的 `collideRemote`），別人的車當作推不動的障礙。
  - 自己的車整個推出重疊，速度只拿兩台車對撞時自己那一份（照兩台車的重量分，一樣重時各一半）。
  - 對方那一份用 `{type:"bump", hits:[{seat, by?, v}]}` 送過去（同一段時間撞到的合成一則），伺服器只轉給開被撞那台車的人，由他加到那台車上。
    撞人的那邊一撞到就把自己推開了，送出去的位置不會疊到對方身上；不送這個的話，被撞的人常常感覺不到被撞。
  - 被撞的人如果自己也算到這次碰撞，同一對車 0.25 秒內只算一次，不會重複加。
  - 延遲大的時候撞起來會軟一點。
- **時鐘**：選完車後伺服器說「還剩幾毫秒起跑」，各自照這個倒數（前兩秒讓大家載入賽道，最後三秒才顯示 3、2、1）。
  - 光靠這個會差很多：瀏覽器忙的時候訊息會晚一兩秒才處理，起跑時間就被算晚了。
    所以再用 `{type:"ping", t}` 對時：伺服器回 `{type:"pong", t, clock}`，取來回最快的那一次，假設伺服器在來回的正中間看時鐘。
    開局時每 0.3 秒一次、對 6 次，之後每 2 秒一次。兩邊的時鐘對準了，別人的車才推算得到現在的位置。
  - 比賽時間照牆上的時鐘走，不是累加每個畫面的時間，切到背景回來時直接跳到現在。所以線上不能暫停，按暫停只是打開選單、放開所有按鍵。
  - 線上每個畫面最多算 0.1 秒的物理（單機是 0.05 秒），慢的裝置（每秒 10 格）車子才不會比別人慢。
- **圈數和成績**由各自的瀏覽器回報（`{type:"lap", lap, time}`），伺服器檢查合不合理：
  - 圈數要一圈一圈來。
  - 回報的時間不能比伺服器的時鐘晚，也最多只能早 3 秒，超過就拉回來。
  - 一圈不能快過「整圈都用噴射極速 80 m/s 跑」（最快的極速型噴射時約 76），最短圈速寫在 `racing.rs` 的 `Track::min_lap_ms`，**改了賽道或車的極速要重算**。
    要算的話，用 rolldown 打包 `track.ts` 印出 `TrackPath.length`。
  - 狀態裡的進度不能多過一路用極速跑的距離，沒跑完的人照這個排名次。

  改用戶端還是可以作弊，但改不出不可能的成績。
- 第一個人跑完後，其他人還有 30 秒可以過線；連著線的人都跑完（或回到房間）就提早結算，整局最多「圈數 × 4 分鐘」。
  名次照完賽時間，沒跑完的照圈數和進度排；第 1 名得「人數」分，每差一名少 1 分，沒跑完的再少 1 分，同一個房間累計。
- 重新整理頁面：伺服器的 view 裡有自己最後送出的狀態（`resume`）和跑完的圈，接著從那個位置跑（速度歸零），不用回到起跑線。
  已經跑完的人和觀戰的人一樣看別人跑，觀戰時可以按「換人」換鏡頭跟的車。
- **跑完後看別人跑**：成績表上按「看別人跑」，成績表收起來，鏡頭用追車視角跟著還在跑的車裡最前面的那台（`RaceGame.spectate`），
  畫面上的名次、圈數、速度都是那台車的；「換人」換下一台，「成績」回到自己的成績。看的那台車不見了（回到房間、斷線）就自動換下一台。
  結算時自動回到成績表。
- **回到房間**：比賽中的選單、成績表上的「回到房間」是離開這局、人留在房間裡（「離開房間」才是真的走），回到選單的大廳等下一局。
  - 還沒結算的話送 `{type:"retire"}`：還沒跑完的算沒跑完（照圈數和進度排名，view 的 `players[].retired` 是 true，成績表寫「回到房間」），
    之後送的狀態、過線都不算，別人畫面上他的車馬上拿掉，也不再輪到他開電腦。結算不等他，所有真人都跑完、回到房間或斷線就結算。
  - 回到房間後這局不會再自動進去（重新整理也一樣，看 `retired`）；選單上顯示「比賽進行中」，可以按「觀看比賽」進去看（沒有座位的觀戰），房主可以中止這局。
- **電腦**：伺服器沒有物理，沒辦法替電腦開車，所以由伺服器指定一位真人（view 的 `driver`）在他的瀏覽器裡開所有電腦，
  用的是單機版的電腦駕駛（`ai.ts`），強弱照電腦的順序分，追趕的對象是還在跑的真人裡最前面的那位。
  - 電腦的狀態跟著他自己的一起送：`{type:"state", d, bots:[[座位, ...狀態]]}`，所以電腦再多每秒也只有 20 則；
    過線用 `{type:"lap", lap, time, bot}` 替電腦回報，檢查規則跟真人一樣，不合理的直接不算、不回錯誤。
  - 撞到電腦的通知轉給他；電腦撞到別人，用 `by` 標出是哪台電腦撞的。
  - 他斷線，或 2 秒沒送電腦的狀態（**切到別的分頁時瀏覽器會暫停畫面**，電腦就停在路上），伺服器就輪給下一位連著線的真人，
    新的人從電腦現在畫的位置和速度接著開。只剩他一個真人時只能等他回來。
  - 他重新整理頁面時，view 的 `botStates` 有電腦最後的狀態，從那裡接著開。
  - 連著線的真人都跑完（或回到房間）就結算，不等電腦；電腦也照名次拿分。

### 機甲對戰

`/games/mecha`：3D 機甲對戰（`frontend/src/games/mecha/`，three.js），只有多人連線，是派對遊戲（`backend/src/mecha.rs`，id `mecha`）。
和 3D 賽車一樣在 `registry.ts` 設了 `fullscreen`，遊戲自己蓋住整個畫面。紅藍兩隊，先擊倒對方 `killTarget` 次（10／20／30／50／100）的隊伍贏，時間到（5／10／15／20／30 分鐘）比擊倒數，一樣就平手。
2～60 人（最多 30 對 30），人不夠可以加電腦（最多 59 台，大廳的「補滿電腦」一次補滿）；選單上的「練習」會直接開房間、加 3 台電腦、按開始，
「大混戰」加 59 台電腦、擊倒目標改成 100 次（15 分鐘）。

- **機甲**（`spec.ts`：每一種的數值在 `MECHS`，大家共用的在 `MECH`）：五種，選隊時每個人自己挑。衝刺（Shift）和飛行共用一條能量，用完要等它回到 15 才能再用；移動和在空中時散布比較大。
  - 速度型「疾風」：耐久 200；走路 15 m/s，Shift 背後兩具推進器噴火衝刺到 34 m/s；空白鍵跳起來、按住往上飛（最高飛到 12 公尺）。
    兩臂的四管速射機砲輪流開火，每秒 10 發、彈匣 60 發、換彈 2.2 秒、射程 230 公尺。模型在 `mech.ts`。
  - 狙擊型「長弓」：四腳的砲台機，耐久 240、打中範圍比較大；沒有推進器（`MechSpec.jets` 是 `null`）：走路 11 m/s，Shift 是快跑（19 m/s，一樣用能量、不噴火），
    空白鍵只能用腳跳一下（大約 1.6 公尺），不能飛，下了河要走坡道上來。
    兩門長管電磁砲輪流開火，1.1 秒一發、彈匣 8 發、換彈 3.2 秒、射程 420 公尺，一發 50（不分遠近）；打中頭（`MechSpec.head`：打中範圍裡面中間的一個小方塊，駕駛艙、感測器那一截）不管對方是哪一種、剩多少血都一發擊倒，擊倒訊息寫「一砲打中頭擊倒」。右鍵開狙擊鏡（視角 16 度，鏡頭移到砲塔裡、自己的機甲不畫，
    轉頭跟著變慢），站穩了開鏡幾乎沒有散布，走動、跳起來就打不準；開砲時鏡頭晃一下、準星往上跳一點。
    模型在 `sniper.ts`：底盤上一座跟著瞄準轉的砲塔，四隻腳用兩節的反向運動學擺（給腳掌要踩的地方算大腿和小腿的角度），走路時對角的兩隻腳一起抬。
  - 偵察型「渡鴉」：兩條反關節長腿撐著駕駛艙，耐久 210；也沒有推進器：走路 14 m/s，Shift 快跑 21 m/s，空白鍵跳一下（大約 2 公尺）。
    脈衝步槍每秒 5 發、彈匣 30 發、換彈 2 秒、射程 260 公尺，一發 11（不分遠近）。模型在 `recon.ts`：頂上的雷達盤一直轉，背上掛兩架偵察機（用掉就看不到）。
  - 偵察型的偵察機（`drone.ts`，數值在 `spec.ts` 的 `DRONE`）：每條命兩架，E 放出去（重生點裡不能放）。放出去後鏡頭跟著偵察機，機甲站著不能動、不能開火。
    WASD 和滑鼠操控（稍微往下看還是平飛，往下看很多才往下衝），空白鍵上升、Shift 下降，最快 26 m/s，撞到大樓會停住，飛不進對方的機庫、
    最高 70 公尺。機身大約 1.8 公尺寬（模型照 `DRONE.scale` 縮小），被打中的範圍是半徑 1.15 公尺的球。左鍵引爆（沒有時間限制）：半徑 9 公尺內看得到爆炸點的敵人一律擊倒（要塞、隕星也一樣）。
    飛多遠都可以，只是離自己的機甲（水平）越遠訊號越差（`DRONE.clear`、`lost`）：200 公尺外畫面開始有雜訊（小張的畫布拉滿畫面）、越來越糊（整個 3D 畫面加 CSS 的 blur、褪色），
    看得到的距離也跟著縮短；340 公尺外整個畫面都是雜訊、什麼都掃不到，畫面中間寫「訊號中斷」，要飛回來一點才看得到。
    操控時再按 E 回到機甲（能動、能開火），偵察機停在原地、鏡頭朝同一個方向繼續掃描，武器欄寫「偵測中」；之後再按 E 回去操控（重生點裡不行）。
    機甲倒下時偵察機跟著掉下去。同時只能有一架在外面。
    在外面的時候一直掃描，只有鏡頭畫面裡看得到的才算：鏡頭前面左右各 34 度、上下各 24 度（畫面中間的掃描框，寬螢幕上大約是畫面中間六成）、
    90 公尺內（訊號差就更近，框上寫現在掃得多遠）、中間沒被擋住的敵人，在自己這隊每個人的畫面上（名牌多一個「◆ 偵測到」，隔著牆、多遠都看得到）
    和小地圖上（外面一圈會閃的圈）標記 6 秒；小地圖上自己這隊的偵察機畫成朝鏡頭方向的扇形。

  放大瞄準時轉頭照視角縮小的比例變慢。
  手機：左下拖曳移動、右半邊拖曳瞄準，右下有開火（按著也能拖曳瞄準）、瞄準（按一下開、再按一下關；狙擊型是狙擊鏡）、衝刺（沒有推進器的是快跑）、跳躍、飛彈、換彈，偵察型多一顆「偵察機」；
  操控偵察機時開火鍵變成引爆、「偵察機」變成回到機甲、跳躍和衝刺變成上升和下降；偵察機停在原地時「偵察機」變成操控偵察機。
  堡壘型、砲擊型多一顆「變身」「架砲」，變身後變成「收回」、衝刺和跳躍收起來。也能接遊戲手把（Y 是偵察機、變身）。瞄準靈敏度在選單裡調，和音效開關一起存在瀏覽器（`games:mecha:*`）。
- **選隊**：房主按開始後有 20 秒選紅隊或藍隊（`{type:"team", team}`）和機體（`{type:"mech", mech:"speed"|"sniper"|"recon"|"fortress"|"mortar"}`，view 的 `players[].mech`）。兩隊人數最多差一個；想去的那隊人比較多時，那隊有電腦就跟電腦交換。
  開局時上一局的人留在原本那隊、開上一局的機體，新來的補到人少的那隊；電腦第一局隨便挑一台。連著線的人都按了「準備好了」（`{type:"ready"}`）或時間到，就倒數 5 秒開打，之後不能換隊。
- **對戰中換機甲**：站在自己家的機庫（重生點）裡，或倒下等復活時，按 B（觸控是「換機甲」按鈕）叫出面板選一台，一樣送 `{type:"mech", mech}`。
  伺服器照最後回報的位置檢查（還沒回報過就是剛出生、在機庫裡）：在機庫裡是馬上換，耐久、飛彈、偵察機補滿，第幾條命加一（還在路上的舊狀態、開火都不算），
  用戶端看到 view 的 `mech` 和 `life` 變了就在原地換成新的一台（放出去的偵察機收回來）；倒下時換的是復活的那台。在外面送會回錯誤。

#### 連線

物理在每個人的瀏覽器裡跑，伺服器只當裁判，不知道大樓在哪裡：

- 每人每秒送 20 次狀態：`{type:"state", d:[時間, x, y, z, vx, vy, vz, 腳的方向, 瞄準水平角, 瞄準仰角, 旗標, 第幾條命, 偵察機的 x, y, z, 偵察機鏡頭的水平角, 仰角]}`（`online.ts` 的 `encodeState`）。
  旗標的低 5 位元是衝刺、開火、在地上、飛行、換彈，再上去 6 位元是主武器開了幾發（除以 64 的餘數）：機砲照「開火中」和射速畫，狙擊型一發一發打，別人照這個數字的變化畫出每一砲；
  再上去一位元是偵察機在外面（沒有時偵察機的那幾個數字是 0），再上去一位元是「這條命的第二架」，再上去一位元（8192）是堡壘型、砲擊型變身了。
  別人的偵察機照收到的位置和鏡頭方向平滑過去，掃描（鏡頭畫面裡看得到誰）、標記敵人每個人在自己這邊算。
  伺服器每 50 毫秒把有更新的機甲、血量變化和這段時間的傷害合併成一則 `{type:"tick", m:[[座位, ...狀態]], hp?, d?:[[開火的, 被打的, 傷害, 0 主武器／1 飛彈／2 偵察機／3 打偵察機／4 迫擊砲彈]]}`。
  別人的機甲照 3D 賽車的做法往前推算到現在（`RemoteMech`），對時一樣用 `ping`／`pong`。狀態裡帶著第幾條命，倒下後還在路上的上一條命的狀態不算。
- **打中**由開火的人的瀏覽器判斷（打他畫面上看到的位置，堡壘型的盾牌擋不擋得住也是），送 `{type:"hit", hits:[{seat, w:"gun"|"missile"|"shell", id?, direct?, head?, by?, drone?}]}`，每 0.1 秒合成一則（一則最多 96 筆）。傷害由伺服器決定：
  `gun` 是主武器，照開火那台的機體算：疾風的機砲 8（100 公尺外慢慢降到 230 公尺的 4），長弓的電磁砲 50，渡鴉的脈衝步槍 11，要塞的機槍 7（110 公尺外慢慢降到 260 公尺的 4），
  隕星的卡賓槍 9；飛彈直接命中 60、爆風 30。三種一擊擊倒（傷害算到剩下的血）：長弓的電磁砲打中頭（`head: true`，別種機甲送了也照平常算）、迫擊砲彈炸到、偵察機爆炸炸到。
  伺服器檢查兩邊都活著、不同隊、不在重生點、距離在射程內（用雙方最後回報的位置；機砲 260、電磁砲 460、脈衝步槍 290、要塞的輕機槍 230、重機槍 290、卡賓槍 220 公尺），
  機砲每秒最多 10 發（最多累積 15 發的寬限）、電磁砲每秒最多 1 發（累積 2 發）、脈衝步槍每秒最多 5 發（累積 8 發）；
  要塞照最後回報的狀態有沒有變身算：輕機槍每秒 6 發（累積 10 發）、重機槍每秒 24 發（累積 36 發）；隕星的卡賓槍每秒 4 發（累積 7 發），架了砲沒有主武器；飛彈要先發射過（`{type:"missile", id, o, dir, target?, goal?}`，`goal` 是準星對到的點，每條命 2 發，伺服器數；同時轉給其他人照一樣的彈道畫出來），
  發射後 8 秒內有效，一發最多打到 3 台、同一台只算一次。
  迫擊砲彈要先發射（`{type:"shell", id, o, v, by?}`，砲口和初速）：要是最後回報的狀態裡變身了的隕星、不在重生點裡、砲口離自己 16 公尺內、初速不超過 150 m/s（用戶端固定 137，不會射太遠）、
  每秒最多 0.5 發（累積 2 發）；伺服器記下彈道，把 `{type:"shell", seat, id, o, v}` 轉給其他人照一樣的彈道畫出來。
  打中是 `w:"shell"`：14 秒內有效，被打的人（最後回報的腳底往上 3 公尺）要在這發砲彈的彈道附近（24 公尺內，`Shell::passes`），一發最多炸到 6 台、同一台只算一次，炸到就擊倒。
  偵察機引爆時送 `{type:"boom", o:[x, y, z], hits:[座位…], by?, n}`：要是偵察型、這條命還有偵察機（view 的 `players[].drones`，引爆、被打下來才少），
  `n`（這條命的第幾架）是現在這一架（已經被打下來的不算），爆炸點離偵察機最後回報的位置不超過 30 公尺（`DRONE_SLACK`；偵察機飛多遠都可以，所以不看離機甲多遠），
  被炸的人（最後回報的腳底往上 3 公尺）離爆炸點 20 公尺內才算（炸到就擊倒），一次最多 4 台；伺服器同時把 `{type:"boom", seat, o}` 轉給其他人畫出爆炸。
  打偵察機是 `drone: true` 的 `gun`（`seat` 是偵察機的主人）：主人最後回報的狀態裡要有偵察機、旗標裡的第幾架要對（打下來、引爆之後還在路上的舊狀態不算），
  離開火的人在射程內、一樣扣主武器的額度；累積 30 就擊落，主人少一架，送 `{type:"downed", seat, by, n}` 給所有人。
  改用戶端還是可以作弊（例如自動瞄準），但打不出超過武器上限的傷害。
- 血量歸零就倒下（`{type:"kill", killer, victim, w}`，`w` 是 gun、head（長弓打中頭）、missile、drone 或 shell），5 秒後在自己的機庫復活：第幾條命加一、滿血、飛彈和偵察機補滿，view 的 `players[].life` 變了用戶端就把機甲放回重生點。
- **電腦**：和 3D 賽車一樣由一位真人（view 的 `driver`）在他的瀏覽器裡開所有電腦（`bot.ts`），電腦的狀態跟著他自己的送（`bots`），電腦打中、發射飛彈用 `by` 標出是哪一台，檢查規則跟真人一樣。
  他每一則狀態都算「還在跑」（電腦都倒下了也會送），2 秒沒收到、或他斷線就換下一位連著線的真人，新的人從電腦現在畫的位置接著開。
  電腦沒看到敵人時沿著路網走向最近的敵人，看到了就邊橫移邊打、保持距離，被打時偶爾衝刺或跳起來閃，瞄準夠久就發飛彈；難度決定瞄得多準、反應多快、轉頭多快。
  開長弓的電腦看得比較遠（390 公尺）、站得比較遠（90～200 公尺），開砲時站穩不橫移，瞄得夠準才開。
  每條命有六成會先爬上自己這一隊大樓的狙擊點（路上看到敵人就邊走邊打），到了就面向河站著等、看到就打，40 秒都沒看到敵人才下去找。
  開渡鴉的電腦站在 45～120 公尺；2.5 秒沒看到敵人、220 公尺內（訊號還清楚的地方）有敵人，就放偵察機：先飛到比目標高 30 公尺越過大樓，鏡頭朝著目標，到了附近俯衝下去引爆（卡住、飛超過 30 秒也引爆）。
  開要塞的電腦看到 25～190 公尺的敵人一陣子就變身站著打，4 秒沒看到敵人就收回來（收回來之後 5 秒內不會再變身）。
  開隕星的電腦每條命有五成多會先爬上自己這一隊大樓的屋頂架砲；不然就往敵人走，看到 110 公尺外的敵人、頭上沒東西擋就架砲。架了砲看得到 520 公尺內的敵人，
  照砲彈要飛多久抓提前量（難度越高抓得越準；電腦給想打的那一點，遊戲照砲口的位置算出砲管要抬幾度），敵人靠到 95 公尺內（太近打不到）、12 秒沒目標（在屋頂上是 40 秒）就收砲。
  電腦和真人一樣不知道砲彈會落在哪裡，不會躲；選目標時不優先挑盾牌正對著自己的要塞。
  30 對 30 時一個人要開 59 台電腦，所以房間每秒最多收 100 則、一則最多 32 KB（電腦的狀態、打中、飛彈都從他那邊送）。
- 線上不能暫停，Esc 只是叫出選單、放開所有按鍵。重新整理頁面時從 view 的 `resume`（自己最後送出的狀態）接著打。沒有座位的人可以觀戰，「換人」換鏡頭跟的機甲。
- 勝場在同一個房間累計（`players[].wins`），結算後的大廳可以再來一局。房間只放記憶體，重啟或換版時進行中的對局會中斷。

### 遊戲狀態

「系統管理 › 遊戲狀態」（`/admin/games`，需要 `admin.users`）：現在開著的線上房間、裡面有誰，以及正在玩單人排行榜的帳號，頁面每 5 秒更新一次
（`backend/src/game_monitor.rs`，三種房間各自的 `snapshot` 提供資料）。

```
GET /api/admin/games  →  {"rooms":[{kind,game,code,phase,round,age_secs,bots,public,events,alive,players:[{who,name,username,online,host,status,ip,online_secs}]}],
                          "solo":[{game,username,score,level,duration_ms,age_secs,idle_secs}]}
```

- 棋類房間列出資料庫裡還沒過期的（包含沒人連著、30 分鐘內還回得來的），另外兩種列出記憶體裡的。電腦玩家只算數量，不列出來。
- 連線時記下來源 IP（和 IP 訪問紀錄一樣取 X-Forwarded-For）與連上的時間，只放在記憶體，斷線就沒了。
- 訪客用來拿回座位的 id 不會送出去，`who` 是它雜湊後的前 8 碼，只用來把同一個人在不同房間的列合在一起。
- 單人排行榜的局 5 分鐘沒回報中間態就不列（暫停、關掉分頁都不會通知伺服器）。對電腦、同一台輪流下、沒登入的單人遊戲只在瀏覽器裡跑，看不到。
- 只看得到接到這個請求的容器：換版的那幾秒新舊容器各有一部分房間。

## 日曆

`/calendar`：月曆（農曆、節氣、節日、放假日標紅）、`/calendar/holidays` 整年的節日與節氣、`/calendar/events` 我的事項。

- 農曆用查表法（`frontend/src/calendar/lunar.ts`，1900–2100 年）。瀏覽器內建的 `Intl` 中國曆在朔日靠近午夜時會差一天（例如 2027 年春節），所以不用它。
- 節氣用 Meeus 的太陽視黃經簡化公式推算（`solarTerms.ts`），以台灣時間為準。
- 放假日依「紀念日及節日實施條例」推算，含補假與 2025 年修法新增的假日（`holidays.ts`）。人事行政總處每年公告的調整放假和補班不能推算，要逐年加到 `ADJUSTMENTS`。
- 個人事項只要登入就能用，每個人只看得到自己的。後端（`backend/src/calendar.rs`）只存事項和重複規則，每一次落在哪天由前端展開（`events.ts`），因為農曆重複要換算農曆。

```
GET    /api/calendar/events          自己的所有事項
POST   /api/calendar/events          新增
PUT    /api/calendar/events/{id}     整筆取代（別人的事項回 404）
DELETE /api/calendar/events/{id}

{ title, note, color, start_date, end_date,       日期 YYYY-MM-DD，end_date 含當天
  repeat, interval, weekdays, until, excluded }  repeat：none / daily / weekly / monthly / yearly / lunar_monthly / lunar_yearly
```

「只刪這一次」是把那次的開始日期加進 `excluded`。修改重複事項會套用到每一次。

## 小工具

除了統一發票對獎要後端代抓中獎號碼，其他都在瀏覽器裡執行。工具登記在 `frontend/src/tools/registry.ts`，每個工具各自打包、進到那一頁才下載。

- **圖片去背**：模型在 Web Worker 裡用 transformers.js 跑，從 Hugging Face 下載後存在瀏覽器快取。
  自動去背用 `Ko033/isnet-general-use-onnx`（WebGPU 用 fp16 約 88 MB，CPU 用 int8 約 46 MB），點選用 `Xenova/slimsam-77-uniform`（第一次點選才下載），兩者都是 Apache-2.0。
  onnxruntime 的 wasm（27 MB，gzip 後約 7 MB）跟著網站部署，不走 CDN；只有舊版 Safari 沒有 WebGPU 時才從 jsdelivr 載入另一個版本。
  Docker 打包時會把大於 1 KB 的 JS／CSS／wasm 等另存一份 `.gz`，後端看到瀏覽器支援 gzip 就直接送壓縮版。
- **匯率計算機**：瀏覽器直接呼叫 Frankfurter v2（`api.frankfurter.dev/v2`，彙整各國央行匯率，含 TWD），最新匯率存在 localStorage，離線時顯示上次的資料。
- **ASCII 藝術字**：figlet 的 `.flf` 字型當成靜態檔輸出，選到才 fetch。
- **Emoji 選擇器**：資料來自 `emojibase-data`（繁中＋英文）。**編碼與雜湊**：雜湊用 `hash-wasm`。
- **證件照產生器**：直接用圖片去背的 worker 和模型，兩邊共用瀏覽器快取。圖片類工具共用的上傳、拖曳、貼上、下載放在 `tools/image-kit/`。
- **照片 EXIF**：直接改檔案的位元組移除中繼資料，不重新壓縮；照片有旋轉時會補回只含方向的 EXIF，避免直拍的照片變橫的。
- **圖片壓縮與轉檔**：在 Worker 裡用 OffscreenCanvas 轉檔，zip 是自己寫的（只打包不壓縮）。
  HEIC 先試瀏覽器內建解碼，不行才動態載入 `heic-to`（LGPL-3.0，約 3.2 MB，所以 `vite.config.ts` 的 chunk 警告上限調到 3300 kB）。
- **QR Code**：產生用 `bwip-js`，掃描沿用 `datamatrix/scanner.ts` 的 `@zxing/library`。
- **簡繁轉換**：`opencc-js` 的詞庫當成靜態檔輸出，選到那個方向才下載（簡轉繁的詞庫 gzip 後約 425 KB）。**文字比對**用 `diff`，**JSON / YAML** 的 YAML 用 `yaml`（動態載入）。
- **正規表示式測試**：在 Worker 裡執行，超過 1.5 秒就終止重開，災難性回溯不會卡住頁面。
- **日期計算**：工作天直接用日曆的 `calendar/holidays.ts`。人事行政總處每年公告的調整放假與補班要登記在那裡的 `ADJUSTMENTS`。
- **薪資試算**：勞保、就保、勞退、職災、健保的級距和費率，以及綜所稅的免稅額、扣除額、級距，都集中在 `tools/salary/rates.ts`，附資料年度和官方來源，**每年要更新**。
  115 年度的基本生活費還沒公告，暫時沿用 114 年度的 213,000。
- **統一發票對獎**：`GET /api/invoice/winning`（`backend/src/invoice.rs`）回傳最近六期的特別獎、特獎、頭獎、增開六獎（有的話）、開獎日與領獎期間。
  號碼來自財政部的 RSS `https://invoice.etax.nat.gov.tw/invoice.xml`（免金鑰）；RSS 沒有領獎期間，最新兩期另外讀稅務入口網的公告頁 `ETW183W2_<期別>` 補上，
  讀不到就用規則推算（開獎隔月 6 日起三個月）。快取在記憶體：單月 25、26 日每 10 分鐘更新，其他時候 12 小時；抓失敗沿用舊資料，前端也會把上次的結果存在 localStorage。
  前端可以輸入末 3 碼快速對、輸入 8 碼直接判定，或用相機掃電子發票證明聯左邊的 QR Code（前 10 碼字軌號碼、接著 7 碼民國年月日，看得出是哪一期）；
  有 BarcodeDetector 就用它，沒有（iOS 等）改用 `@zxing/library` 解取景框裡的畫面，HTTP 網站沒有相機就改成拍照。對過的號碼存在 localStorage，還沒開獎的期別開獎後會自動對。
- **計時器**：番茄鐘、碼表、倒數。時間都存開始／結束的時間戳（`performance.timeOrigin + performance.now()`），顯示時才相減，背景分頁也不會慢；
  時間到只排一個 `setTimeout` 等到結束那一刻，響 Web Audio 合成的鈴聲並發系統通知（第一次按開始時詢問權限），分頁標題顯示剩餘時間。進行中的計時存在 localStorage，重新整理會接著跑。
- **抽籤・分組**：分成 N 組或每組 M 人，人數差不超過 1；「一定要分開」的人先放，衝突時整個重來，最多試 300 次。

## Threads 影片下載

`/threads`（只有登入的人看得到）：安裝捷徑、複製自己的下載金鑰、看下載紀錄。在 Threads 按「分享 → Threads 影片下載器」，
捷徑把網址和金鑰丟給 API，再下載回傳的 mp4 存進相簿。後端在 `backend/src/threads.rs`，前端在 `frontend/src/threads/`。

- 捷徑只有一個，大家共用：管理員在 iPhone 做好、分享成 iCloud 連結，貼到 `/threads` 頁面下方（存在 `site_settings.threads_shortcut_url`）。
  iOS 15 之後只能安裝簽署過的捷徑，簽署要用 Mac 的 `shortcuts sign`，伺服器沒辦法替每個人產生一份，所以改成每個人一把金鑰。
- 金鑰每個帳號一把（`threads_keys`，存原文，頁面上隨時能複製），可以換新的，舊的馬上失效；停用的帳號金鑰也不能用。
  捷徑第一次執行時要求貼上，存在 iCloud 雲碟「捷徑」資料夾的 `ouyang-threads-key.txt`，之後放在 `X-Threads-Key` 標頭送來（不放網址，才不會進到 IP 訪問紀錄）。
  金鑰錯誤的訊息一定有「金鑰」兩個字，捷徑看到就刪掉存著的金鑰，下次重新詢問。
- 查到影片就記一筆在那個帳號的下載紀錄（`threads_downloads`：貼文網址、作者、說明前 300 字、影片數），每個帳號留最近 500 筆，可以刪除。
- **貼網址下載**（`/threads/paste`）：不用捷徑，直接在網頁貼上網址，電腦和 Android 也能用。打同一支 API，沒帶金鑰就用登入的帳號，一樣記在下載紀錄。
  - 空的輸入框貼上會直接送出，也可以用 `/threads/paste?url=<網址>` 帶進來。前端先檢查是不是 Threads 或 YouTube 的網址才送出，查完倒數 10 秒，免得白白吃掉冷卻時間。
  - 預覽和下載都由瀏覽器直接跟 Meta CDN 拿（影片和封面都有 `Access-Control-Allow-Origin: *`），不經過我們的伺服器。
    手機用分享選單存（iPhone 選「儲存影片」進相簿），電腦直接存成 `threads_<作者>_<代碼>.mp4`。

```
GET    /api/threads/video?url=<貼文或分享連結>     標頭 X-Threads-Key: <金鑰>（網頁沒帶就用登入的 session）
→ 200 {"source","code","author","caption","videos":[{"url","thumbnail","width","height"}]}   輪播有幾支影片就有幾筆
       source 是 threads 或 youtube；YouTube 的 code 是影片 id、author 是頻道名稱、caption 是標題
→ 401 {"error"}                    沒帶金鑰也沒登入，或金鑰無效（有帶金鑰就只看金鑰）
→ 400 {"error"}                    不是 Threads／YouTube 的網址、找不到貼文、沒有影片（或要登入才看得到）、YouTube 影片太長或有年齡限制
→ 429 {"error","retry_after":10}   同一個 IP 10 秒只能查一次（不管成功與否），回應帶 Retry-After
→ 503 {"error"}                    Threads 連不上；YouTube 擋下伺服器，或正在下載別的影片
GET    /api/threads/files/{代碼}         YouTube 下載好的 mp4（不用登入，代碼是隨機的，1 小時後失效），支援 Range

GET    /api/threads/setup               {"key","shortcut_url"}   第一次來就產生金鑰（要登入）
POST   /api/threads/setup/key           換一把新的金鑰
PUT    /api/threads/setup/shortcut      {"url"}  共用捷徑的 iCloud 連結，空字串是清掉（要 admin.users）
GET    /api/threads/downloads           自己的下載紀錄，新的在前
DELETE /api/threads/downloads/{id}
```

- url 可以是一整段文字（分享時可能連貼文內容一起送來），取第一個 Threads 網址。
- 只接受 `threads.com`／`threads.net` 的 https 網址，分享連結（`/share/xxx`）的轉址也只跟到 Threads 自己的網址，不會被拿來打其他主機。
- Threads 沒有查別人貼文的公開 API，一般瀏覽器拿到的頁面也沒有貼文資料（登入後由前端另外查），
  只有搜尋引擎拿到的頁面把資料放在 `<script type="application/json">` 裡，所以用 Googlebot 的 User-Agent 抓，從裡面找這則貼文的 `video_versions`。
  非公開格式，Meta 改版時要跟著調整。沒登入看不到的內容抓不到，例如引用了限制瀏覽的貼文（`quoted_attachment_post_unavailable`）。
- 回傳的是 Meta CDN 的網址，帶簽章、幾天後失效，不用 cookie 就能下載；影片不經過我們的伺服器。
- **YouTube**（`backend/src/youtube.rs`）：url 裡有 YouTube 影片網址（`watch?v=`、`youtu.be/`、`shorts/`、`live/`）就改走這裡，金鑰、冷卻時間、下載紀錄都共用。
  - YouTube 的串流網址綁下載者的 IP、影音分開，所以由伺服器用 yt-dlp 下載，ffmpeg 合併成 H.264 + AAC 的 mp4（iPhone 相簿收得下），
    yt-dlp 還要 Deno 解 YouTube 的簽章。三個執行檔都在 Docker image 裡（distroless 沒有 Python，用 PyInstaller 版的 yt-dlp，另外補 libz）。
    本機開發要自己裝：`pip install "yt-dlp[default]" deno`，ffmpeg 放 PATH；`YTDLP` 環境變數可以指定 yt-dlp 的路徑。
  - 只抓公開影片，最長 20 分鐘、最高 1080p、1 GB 以下，直播不行；同時只跑一個下載，超過 5 分鐘砍掉。
  - 下載好的檔案放在暫存資料夾（容器的 `/tmp/ouyang-youtube`），回傳 `{origin}/api/threads/files/<隨機代碼>`，捷徑和網頁都從這裡拿；
    1 小時後刪除，重開伺服器也會清空。換版時新舊容器各有自己的檔案，剛好在換版那一刻查的影片可能拿不到，重查一次就好。
  - **YouTube 改版時 yt-dlp 會壞掉**：到 [yt-dlp releases](https://github.com/yt-dlp/yt-dlp/releases) 看新版號，改 Dockerfile 的 `YTDLP_VERSION` 重新部署。
  - YouTube 常擋資料中心的 IP（「Sign in to confirm you're not a bot」），擋下時回 503，只能過一陣子再試。
  - 下載和合併時 yt-dlp、Deno、ffmpeg 加起來最多大約 200 MB 記憶體（160 MB 時會卡在解析階段），跟後端算在同一個容器的 `mem_limit` 裡，所以 prod／staging 的 `MEM_LIMIT` 各加了 192 MB。

## 短網址

`/links`（只有登入的人看得到）：把長網址變成 `https://ouyang.app/s/<代碼>`，詳細頁有 QR Code（複製、分享、下載 PNG／SVG）和點擊統計。
後端在 `backend/src/short_links.rs`，前端在 `frontend/src/links/`，QR Code 沿用小工具的 `tools/qrcode/matrix.ts`。

```
GET    /s/{code}                  303 跳到目的網址並記一筆點擊；要登入的短網址沒登入時導到 /login?next=/s/{code}；找不到回 404
GET    /api/links                 自己的短網址（含點擊數、不同 IP 數、最後一次），新的在前
POST   /api/links                 {"url","code","title","require_login"}  →  201   code 空的就隨機產生；撞到別人的回 409
GET    /api/links/{id}
PUT    /api/links/{id}            {"url","title","require_login"}   代碼不能改，印出去的 QR Code 才不會失效
DELETE /api/links/{id}            點擊紀錄一起刪掉
GET    /api/links/{id}/stats      {"link","ips":[…],"clicks":[…],"days":[{day,clicks}]}   前 300 個 IP、最近 300 次、最近 30 天每天的次數
```

- 隨機代碼 4 碼，用小寫英文加數字並去掉 0 o 1 l i；撞到就重抽，一直撞才多一碼。自訂代碼是 2～32 個英數字、`-`、`_`，大小寫有分。
- 網址只接受 http／https，沒寫 scheme 當 https。每個帳號最多 500 個，只看得到、改得到自己的（別人的回 404）。
- 「要登入」只是要求登入本站任何帳號，不限建立的人。登入頁看到 `?next=`（只接受站內路徑）會在登入後整頁跳過去，交給後端處理。
- 每一次跳轉記下 IP（Traefik 的 X-Forwarded-For）、帳號、User-Agent 和 Referer，存在 `short_link_clicks`，保留 180 天。
  跳轉帶 `Cache-Control: no-store`，瀏覽器不會快取，每次都算得到。同一個 IP 10 分鐘超過 200 次的部分照樣跳轉但不記。
- 本機開發時 Vite 也把 `/s/` proxy 到後端。

## IP 訪問紀錄

「系統管理 › IP 訪問紀錄」（`/admin/access`，需要 `admin.users`）：全站每個請求的來源 IP、方法、路徑、狀態碼、花費時間、登入的帳號和 User-Agent，
可以依 IP 彙整（依最後活動或請求數排序，展開看那個 IP 的請求），或看最近 500 筆請求。程式在 `backend/src/access_log.rs`。

```
GET /api/admin/access?hours=24&sort=recent|requests   統計、前 300 個 IP、請求最多的 15 個路徑      hours：1～720
GET /api/admin/access/requests?hours=24&ip=&errors=   最近 500 筆請求（可以只看某個 IP、只看 4xx／5xx）
```

- 用 middleware 記錄，IP 跟登入限制一樣取 Traefik 的 X-Forwarded-For。前端打包出來的靜態檔（`STATIC_DIR` 最上層有的檔案和資料夾）、
  `/api/health` 和這個頁面自己的查詢不記；不存在的路徑（掃描器找的 `/wp-login.php`、`/.env`）會記。
  前端沒有點開頭的路徑，所以 `/.git/config` 這類直接回 404，不會拿到 index.html（`lib.rs` 的 `hide_dot_paths`）；`.env` 會拿到假的設定檔，見下面的 .env 蜜罐。
- 請求本身不碰資料庫：先放在記憶體，背景每 2 秒整批寫進 `access_logs`，帳號也是那時才從 session 查（登入那一次還沒有 cookie、
  登出那一次 session 已刪，都算訪客）。關機時會寫完剩下的，被強制結束的話最後幾秒會遺失。
- 保留 30 天，每小時清一次。同一個 IP 10 分鐘超過 1000 筆的部分不記，避免被灌爆。

## .env 蜜罐

掃描器常來找 `/.env`、`/.env.local`、`/api/.env` 這類設定檔想偷資料庫密碼和金鑰。這些網址會回一份假的設定檔，並記下是誰拿走的，
在「系統管理 › .env 蜜罐」（`/admin/honeypot`，需要 `admin.users`）看：每個 IP 來了幾次、找過哪些路徑、裝置，展開看每一次的時間和網址；
誰拿假密碼來登入；哪些 IP 現在被擋。程式在 `backend/src/honeypot.rs`。

```
GET    /api/admin/honeypot              統計、最近的 300 個 IP、被找最多次的 30 個路徑、最近 100 次用假密碼登入（uses）、
                                        現在被擋的 IP（blocks，手動的在前面）、自動封鎖有沒有開（auto_block）
GET    /api/admin/honeypot/hits?ip=     最近 500 次（可以只看某個 IP）
PUT    /api/admin/honeypot/auto-block   {"enabled":false}  →  {"enabled":false}
POST   /api/admin/honeypot/blocks       {"ip":"203.0.113.5","days":7,"note":"…"}  →  201   days 不給或 null 是永久
DELETE /api/admin/honeypot/blocks/{ip}  解除封鎖（手動和自動都解）  →  204
```

- 路徑最後一段是 `.env` 或 `.env.<任何字>` 都算，在哪一層底下都一樣（`/laravel/.env`、`/.env.production`…），任何 method 都回同一份。
  用最外層的 middleware 攔，所以 `/api/.env` 也會被攔到；`.envrc`、`/.git/config` 這類照舊回 404。
- 假檔案裡的主機是連不到的內網 IP，密碼和金鑰由啟動時隨機產生的金鑰和來源 IP 算出來，跟真正的設定無關，也不在 git 裡。
  每個 IP 拿到的都不一樣，同一個容器裡同一個 IP 每次拿到的一樣，看起來才像真的。
- 紀錄存在 `honeypot_hits`，保留 180 天；帳號是當時有登入的人（通常是管理員自己點開來看）。同一個 IP 10 分鐘超過 200 筆的部分不記，照樣回假檔案。
- IP 訪問紀錄也會記到這些請求，狀態碼是 200。

### 假密碼被拿去用

- 發出去的 `DB_PASSWORD`、`REDIS_PASSWORD`、`SMTP_PASSWORD`、`ADMIN_PASSWORD`（帳號 `sysadmin`）記在 `honeypot_secrets`，連同是發給哪個 IP 的。
  有人拿其中一個來 `/api/auth/login`，不管填什麼帳號都記一筆到 `honeypot_uses`：哪個 IP 來用、用了哪一行、當初是哪個 IP 拿走的。
  對方看到的跟一般的密碼錯誤一樣（401「帳號或密碼錯誤」）。兩邊 IP 不同很常見，掃描和實際動手的常常是不同台機器。
- 同一個 IP 10 分鐘超過 200 次的部分不記。兩張表都保留 180 天。
- 可以再放一組 [canarytokens.org](https://canarytokens.org) 的假 AWS 金鑰（建立 token 時選 AWS keys），有人拿去呼叫 AWS 時
  canarytokens 會寄信通知，信裡有對方的 IP。在伺服器的 `secrets.env` 加上下面兩行，下次部署後假檔案裡就會多出 `AWS_ACCESS_KEY_ID` 這幾行；沒設定就不放：
  ```
  HONEYPOT_AWS_ACCESS_KEY_ID=AKIA...
  HONEYPOT_AWS_SECRET_ACCESS_KEY=...
  ```

### 封鎖

被擋的 IP 不能登入也不能註冊，錯誤訊息跟失敗太多次、申請太多次一樣，不讓對方知道原因。其他頁面照常能看。

- **自動封鎖**（預設開著，管理頁可以關，存在 `site_settings` 的 `honeypot_auto_block`）：最近 24 小時拿過假檔案（有登入的那幾次不算）
  或用過假密碼的 IP。第一次用假密碼還是回 401，之後才開始擋。
  30 天內有帳號在那個 IP 登入過的不擋（看 IP 訪問紀錄裡有沒有帶帳號的請求），所以管理員登出後點開 `/.env` 來看，不會把自己鎖在外面。
  關掉時照樣記錄誰來拿、誰用假密碼，只是不擋。
- **手動封鎖**（`honeypot_blocks`）：管理頁輸入 IP、期限（1 / 7 / 30 天或永久）和備註；表格裡沒被擋的 IP 旁邊的「封鎖」會把 IP 填進表單。
  不管自動封鎖有沒有開、那個 IP 有沒有帳號登入過都擋。IP 存成標準寫法（IPv6 小寫、縮寫），不能封鎖自己目前的 IP。
- 被擋的 IP 旁邊有「封鎖中」或「手動封鎖」和「解除封鎖」。手動的直接刪掉；自動的把解除時間記在 `honeypot_pardons`，
  那之前的紀錄不再算，之後再來拿還是會被擋。
- 封鎖是每次登入、註冊時從資料庫算出來的，換版、重啟都照樣有效，換版期間的新舊容器結果也一樣。

## 主機監控

「系統管理 › 主機監控」（`/admin/system`，需要 `admin.users`）：整台主機的 CPU（含 iowait、steal）、記憶體、磁碟用量與讀寫、網路、負載，
以及主機上每個服務各用了多少 CPU 和記憶體，頁面每 5 秒更新一次。程式在 `backend/src/monitor.rs`。

```
GET    /api/admin/system                 目前的快照（snapshot，讀不到 /proc 時是 null 加上 error）、監控清單的狀態（targets）
GET    /api/admin/system/history?range=  1h：每 5 秒一點；24h：每分鐘一點；7d：每 10 分鐘一點    {"step_secs","points":[{t,cpu,mem_used,rx_bps,tx_bps,read_bps,write_bps,targets:[…]}]}
POST   /api/admin/system/targets         {"label":"歐陽小俠","pattern":"Xiao-Xia"}  →  201   最多 20 個
DELETE /api/admin/system/targets/{id}
```

- 全部讀 Linux 的 /proc。容器裡的 /proc 只看得到自己，所以 `compose.yaml` 把主機的 /proc 唯讀掛到 `/host/proc`（`HOST_PROC`）。
  容器是 nonroot，讀得到每個行程的 stat、cmdline、cgroup，讀不到環境變數。本機開發（Windows、macOS）沒有 /proc，頁面會顯示讀不到。
- 行程依 `/proc/<pid>/cgroup` 分組：同一個 systemd 服務、Docker 容器或 SSH 工作階段（tmux、nohup 跑的）算一組，主機上的 bot 不用設定就會出現。
  Docker 容器只知道 id（讀不到 docker socket），所以用主要行程的指令列當名稱。CPU 一律換算成佔整台主機的比例。
- 監控清單存在 `monitor_targets`：cgroup 路徑或指令列含有關鍵字（不分大小寫）的行程都算，一個都沒有就標成「沒在跑」。
  bot 用 systemd 跑的話關鍵字填 `<名稱>.service`；容器的 id 每次部署都會換，改填指令列的一部分。
- 磁碟是資料庫所在的分割區（容器的 `/data` volume，在 EC2 上就是根目錄那顆 EBS）；網路讀主機 1 號行程的 `/proc/1/net/dev`，不算 lo 和 docker 的虛擬網卡。
- 背景每 5 秒取樣。最近 1 小時的 5 秒點只放在記憶體；每分鐘的平均寫進 `monitor_points`（保留 7 天），24 小時和 7 天的圖從資料庫讀，
  換版重啟後也還在，1 小時的圖剛重啟時前面用分鐘點補。分鐘點對齊整分鐘，換版時新舊容器都會寫同一分鐘，留取樣點多（`samples`）的那筆。
  圖的橫軸照時間比例，停機超過兩三個點的區段會斷開。staging 和 prod 各自取樣、各存各的資料庫，看到的是同一台主機。
  這個頁面的請求不記進 IP 訪問紀錄。

## 隱藏頁面

不在任何選單、首頁或工具清單裡，只有知道網址的人進得來；頁面加了 `noindex`。誰來過記在「系統管理 › 頁面訪客」（`/admin/visits`，需要 `admin.users`）。

- **`/bcs` Data Matrix 生成器**：倉位（SLOC / BIN / STYP）和料件（MODEL / MO / QTY / DC / SER）兩種內容產生 Data Matrix，最愛和歷史存在 localStorage。
  掃描在支援 BarcodeDetector 的瀏覽器即時掃相機，其他（iOS）改成拍照後解碼，解不出來再用 ZXing。相機和 BarcodeDetector 都只在 HTTPS 能用，HTTP 下一律走拍照。

```
POST /api/visits/{page}                  {session, action, detail}   action：open / click / scan / error，不用登入
GET  /api/admin/visits/{page}            統計和最近 300 次瀏覽（每個分頁一次）
GET  /api/admin/visits/{page}/{session}  那次瀏覽的事件
```

- 前端用 `useVisitTracking`（`frontend/src/visits.ts`）：進頁面送 open，頁面裡的按鈕被點送 click（名稱取 `data-track` 或按鈕文字），JS 錯誤送 error（每次瀏覽最多 20 筆）。
- 後端補上來源 IP（Traefik 的 X-Forwarded-For）、登入的帳號和 User-Agent，存在 `page_events`，保留 180 天。同一個 IP 10 分鐘超過 200 筆就不再記。
- 新增隱藏頁面：在 `backend/src/visits.rs` 的 `PAGES` 加上 id，頁面裡呼叫 `useVisitTracking('<id>', rootRef)`。

`/music`：播放伺服器上一個資料夾裡的音樂，`/music/favorites` 是收藏。檔案由 Discord bot（Xiao-Xia）放進
`~/Xiao-Xia/data/attachments/572417837537296396`，`compose.yaml` 把它唯讀掛到容器的 `/music`（路徑寫在 `<env>.env` 的 `MUSIC_HOST_DIR`，staging 和 prod 共用同一個資料夾）。

GET /api/music/files/{name}    檔案本身，支援 Range（拖曳進度）

  連到網頁的話不會。手機用系統的分享選單，電腦直接複製。
  Telegram 只幫網域產生預覽（貼 IP 的不會），路徑裡有中文的也不會（編不編碼都一樣），
  所以檔名不是單純英數字時改用 `/api/music/s/` 的十六進位網址，例如 `三蛋一體.mp3` → `/api/music/s/E4B889E89B8BE4B880E9AB94.mp3`。

## 天氣與環境

`/weather`：總覽、`/weather/typhoon` 颱風、`/weather/forecast` 全台天氣、`/weather/quake` 地震。後端在 `backend/src/weather/`，外部資料都由後端抓、整理過再給前端。

```
GET /api/weather/typhoons      颱風（各來源合併）  快取 10 分鐘，背景每 8 分鐘重抓
GET /api/weather/forecast      22 縣市天氣與空氣品質  快取 15 分鐘，背景每 13 分鐘重抓
GET /api/weather/quakes        最新速報、各國地震報告、速報連線狀態  報告快取 3 分鐘，背景每 2 分鐘重抓
GET /api/weather/quakes/ws     即時速報  server → client  {type:"snapshot", eew:[...]}、{type:"eew", eew}
```

- 伺服器啟動後就在背景定時重抓（間隔比快取時間短），有人來看時直接回現成的資料，不用等外部 API（颱風一次要好幾秒）。
  背景沒跟上、快取過期時才由請求自己去抓，同一時間只有一個請求真的打外部 API；外部來源掛掉時繼續回上一次成功的資料，頁尾標出哪個來源暫時連不上。
- **颱風・官方路徑**：日本氣象廳（過去路徑、強度、70% 機率圓、暴風圈）、GDACS 整理的 JTWC／NHC（全球，含不確定範圍）、中央氣象署（要金鑰）。
  各來源的颱風依目前位置合併（600 公里內視為同一個）。GDACS 在颱風消散後還會掛一陣子，美國那邊用 NHC 自己的清單過濾。
- **颱風・AI 系集**：Google DeepMind Weather Lab 的系集預報（`OPER` 模型，每 6 小時起報，發布比起報晚 6～8 小時），平均路徑加上 50 個成員。即時資料受其使用條款約束，頁面上有標示。
  官方和 AI 畫在同一張圖，用圖層開關分別顯示或隱藏（AI 的開關記在 localStorage）。
- **首頁颱風區**：西北太平洋有官方資料的颱風才出現，地圖（Leaflet）在那時才下載。
- **天氣**：Open-Meteo（免金鑰，一次請求查 22 縣市），空氣品質是美國 AQI。
- **地圖底圖**：Esri 的淺灰／深灰 Canvas，跟著主題切換（CARTO 已經要金鑰）。線條顏色用 CSS class 控制，才吃得到主題變數。
- **地震速報**：伺服器一啟動就連 wolfx 的 `cwa_eew`、`jma_eew`、`sc_eew`、`fj_eew`，經過主機上的 relay（`EEW_RELAY_URL`，和歐陽小俠共用同一條上游）。
  wolfx 同一個 IP 大約只給 5 條 WebSocket，所以只連小俠也在用的這 4 個，地震清單改用 HTTP；relay 連不上時也**不會**改成直連，避免和 relay 搶連線。
  沒設 `EEW_RELAY_URL`（本機開發）就直接連 wolfx。台灣速報的 HTTP 版被 Cloudflare 擋，啟動後要等推送才有資料。
- **地震報告**：USGS（台灣附近 M3+、全球 M4.5+）、wolfx 轉的日本氣象廳與中國地震台網清單、中央氣象署（要金鑰）。
- 地震頁的 S 波倒數與當地震度是用 3.5 km/s 和台灣常用的 PGA 衰減式粗估，「測試速報畫面」按鈕只在自己的瀏覽器裡模擬一筆。
- **全站速報**：每一頁都連著 `/api/weather/quakes/ws`（`weather/quakeFeed.tsx`，整個分頁共用一條，地震頁也用它），
  速報會跳在固定的頁首底下（`weather/QuakeAlert.tsx`）。不分來源，依使用者選的縣市（和地震頁同一個設定）判斷：
  震央在 60 km 內一律跳（和 eew_linebot 一樣），再遠的看預估當地震度，2 級以上才跳；距離算到震源（含深度），深層地震才不會高估。
  發震 3 分鐘後或按 ✕ 就收起來，地震頁本身有完整的速報卡所以不重複顯示。按「測試速報畫面」後切到別頁，可以看頁首的樣子。

## AI

「系統管理 › AI 設定」（`/admin/ai`，需要 `admin.users`）：設定好幾組 OpenAI 相容的 API（vLLM、Ollama、OpenAI…），
選一組給全站的 AI 功能使用，同一頁可以挑任一組直接對話測試。程式在 `backend/src/ai.rs`，前端共用的在 `frontend/src/ai/`。

```
GET    /api/ai/status                    使用中那一組能不能用  {"configured","available","since","checked_at"}   不用登入、不含錯誤細節
GET    /api/admin/ai                     {"active_id","providers":[{id,name,base_url,model,key_hint,status,events}]}
POST   /api/admin/ai/providers           {"name","base_url","api_key","model"}  →  201   最多 20 組，第一組自動設成使用中
PUT    /api/admin/ai/providers/{id}      同上；api_key 不給（null）就沿用原本的，空字串是清掉
DELETE /api/admin/ai/providers/{id}      使用中的那一組不能刪（409）
PUT    /api/admin/ai/active              {"id":3}，null 是停用全站的 AI 功能
POST   /api/admin/ai/check               每一組馬上重新檢查
POST   /api/admin/ai/models              {"base_url","api_key"?,"provider_id"?}  列出伺服器上的模型（存之前先選），上游出錯回 502
POST   /api/admin/ai/chat                {"provider_id"?,"messages":[{role,content}],"thinking"?}  回 NDJSON 串流
```

- 設定存在 `ai_providers`，使用中的是 `site_settings.ai_active_provider`。金鑰只留在伺服器，API 只回最後 4 碼（`…abcd`）。
  `base_url` 是含 `/v1` 的那一段（例如 `http://host:15002/v1`），結尾的 `/` 會拿掉。
- 改網址時沒有重填金鑰，「讀取模型」不會把存著的金鑰送到新網址。
- **狀態**：背景每 15 秒對每一組打 `GET {base_url}/models`，連不上、金鑰錯（401／403）、網址錯（404）、伺服器錯誤或模型不在清單上都算異常；
  真的呼叫時失敗也立刻標成異常，成功就恢復。狀態只放在記憶體，每個容器各自檢查，管理頁看得到每一組最近 30 次的狀態變化。
  4xx（例如輸入太長）只算這次請求失敗，不算服務掛掉。`/api/ai/status` 不記進 IP 訪問紀錄。
- **告訴使用者**：AI 功能的頁面最上面放 `<AiStatusNotice />`（`frontend/src/ai/AiStatusNotice.tsx`），使用中那一組不能用時顯示「AI 服務暫時無法使用」，
  沒選任何一組時顯示「AI 功能尚未開放」，能用時什麼都不顯示。它每 15 秒問一次 `/api/ai/status`（分頁在背景時暫停，整個分頁共用一份），
  AI 呼叫失敗時 `streamChat` 也會馬上重問，恢復後自己消失，不用重新整理。
- **串流**：上游一律用 `stream: true`，後端整理成一行一個 JSON 給前端：
  `{type:"reasoning",text}`（思考）、`{type:"content",text}`（答案）、`{type:"done",finish_reason,usage}`、`{type:"error",message}`。
  思考內容支援 vLLM 的 `reasoning_content`／`reasoning`，以及沒開 reasoning parser 時包在答案最前面的 `<think>…</think>`。
  前端關掉連線（離開頁面、按停止）時後端也會斷開上游，上游就不會繼續生成。
- `thinking: false` 會送 `chat_template_kwargs.enable_thinking = false`（vLLM 上 Qwen3 這類模型關掉思考），不指定就不送這個欄位，別的伺服器才不會不認得。

### 新增 AI 功能

1. 後端用 `state.ai.complete(&state.pool, &messages, &options)` 等整段回答（`content` 不含思考），
   或 `state.ai.stream(...)` 拿到一段一段的 `Event`，再用 `ai::ndjson(rx)` 串流給前端。都用使用中的那一組，不用管網址和金鑰。
2. 錯誤直接 `?` 轉成 `AppError`：沒設定回「AI 功能尚未開放」、掛了回「AI 服務暫時無法使用」（都是 503），不會把上游的網址和錯誤細節給一般使用者。
   handler 要拿 `CurrentUser`（只給登入的人），開始前呼叫 `ai_usage::begin(&state, &user, true)` 檢查額度、拿到 `RunGuard`，
   結束後 `ai_usage::record(...)` 記用量（見下面的「用量與額度」）。
3. 前端頁面最上面放 `<AiStatusNotice />`，串流用 `streamChat(path, body, onEvent, signal)`（`frontend/src/ai/api.ts`），
   要依狀態停用按鈕的話用 `useAiStatus()`。

### AI 助手（`/ai`）

登入才能用的對話 APP（`loginOnly`），AI 可以呼叫工具查資料、操作本站功能。對話存在資料庫，每個人只看得到自己的。
後端：`ai_chat.rs`（對話與 agent loop）、`ai_tools.rs`（工具登記）、`ai_builtin.rs`（內建工具）、`mcp.rs`（MCP 客戶端）；
前端：`frontend/src/ai/chat/`。

```
GET    /api/ai/chats                     自己的對話  [{id,title,updated_at,pending}]
POST   /api/ai/chats                     開新對話（順便清掉沒說過話的空對話）
GET    /api/ai/chats/{id}                整段對話 {…, messages:[{role,content,reasoning,tool_calls,tool_*,status,usage}]}
PATCH  /api/ai/chats/{id}                {"title"} 改名
DELETE /api/ai/chats/{id}
POST   /api/ai/chats/{id}/messages       {"content","thinking"?}  回 NDJSON 串流
POST   /api/ai/chats/{id}/approve        {"decisions":[{id,approve}]}  確認或拒絕等待中的動作，接著做，回 NDJSON 串流
GET    /api/ai/tools                     自己的對話裡能用的工具 {supported,tools}
GET    /api/ai/usage                     自己今天的用量和額度
POST   /api/ai/calendar/parse            {"text"}  一句話變成日曆事項的草稿（不會存）
```

- **agent loop**：把對話和能用的工具（OpenAI 的 `tools` 格式）交給模型；模型要呼叫工具就執行、把結果放回對話再問一次，
  直到模型直接回答，最多 8 輪。每一步（AI 的回答、要呼叫的工具、工具結果）都存進 `ai_chat_messages`，給模型的對話太長時從前面整段丟掉。
- **確認**：會改資料的工具（新增／修改／刪除事項、建立短網址）不會直接執行，存成 `pending` 讓這次串流結束，
  畫面上出現「允許／拒絕」，按了才走 `/approve` 接著做。還在等確認時直接問別的，等待中的動作當作拒絕。
  工具一律以目前登入的使用者身分執行，跟自己在網頁上操作一樣。
- **串流事件**：`step`（新的一輪）、`reasoning`、`content`、`tool_call`、`tool_result`、`approval`（有動作在等確認）、
  `title`（第一次回答完 AI 取的標題）、`done`、`error`。使用者按停止（關掉連線）時後端停止生成，已經產生的部分存成 `stopped`。
- **工具呼叫要伺服器支援**：vLLM 要加 `--enable-auto-tool-choice --tool-call-parser hermes`（Qwen3 用 hermes）。
  沒開的話帶 `tools` 會被拒絕（400），`ai.rs` 會記下這一組不支援，改成不帶工具重送，AI 助手變成一般聊天；
  「AI 工具」頁和 `/api/admin/ai` 的 `tools` 看得到。改設定（重新儲存那一組）後會重新偵測。
- **內建工具**：日曆（查、新增、修改、刪除）、國曆農曆換算（`lunar.rs`，跟前端同一份表）、天氣預報、颱風、地震、
  統一發票對獎、短網址（查、建立）。都是直接呼叫站上現有的 handler，結果太長會截到 16,000 字。
- **搜尋本站功能（`site_search`）**：只在瀏覽器裡跑的小工具、小遊戲後端沒辦法執行，但 AI 可以查有哪些、給連結。
  `npm run build` 最後一步（`frontend/scripts/site-catalog.mjs`）用 Vite 載入 `apps/`、`tools/`、`games/registry.ts`，
  產生 `dist/site-catalog.json`（名稱、說明、網址、標籤、分類、APP 底下的頁面），後端從 `STATIC_DIR` 讀。
  新增 APP、工具或遊戲只要登記進 registry，AI 就查得到。要權限的 APP（系統管理）只有有權限的人查得到；
  前端還沒 build 時工具回「還沒有功能清單」，不會影響其他工具。

```
GET    /api/admin/ai/tools               {servers, tools:[{name,title,kind,enabled,approval,default_approval}], provider_tools}
PUT    /api/admin/ai/tools/{name}        {"enabled","approval"}  開關工具、改要不要確認（改回預設就刪掉設定）
POST   /api/admin/ai/mcp                 {"name","prefix","url","headers":[{name,value}],"enabled","public"}  新增並讀取工具
PUT    /api/admin/ai/mcp/{id}            同上；header 的 value 給 null 是沿用原本的值（改了網址就不沿用）
DELETE /api/admin/ai/mcp/{id}
POST   /api/admin/ai/mcp/{id}/refresh    重新連線、重新讀工具清單
```

- 只支援 **Streamable HTTP**（`POST` JSON-RPC，回應是 JSON 或 SSE）。容器是 distroless，跑不了 stdio 的伺服器（`npx`、`uvx`），
  要用的話在別台主機用 supergateway 之類的轉成 HTTP 再接進來。session（`Mcp-Session-Id`）放在記憶體，過期（404）會自己重新 initialize。
- header（例如 `Authorization: Bearer …`）存在 `ai_mcp_servers.headers`，API 只回名稱和最後 4 碼。
- **開放給所有登入的人**預設不勾：沒勾的伺服器只有管理員的對話裡有，因為伺服器上的金鑰是管理員的，不能讓每個人都拿去用。
- 預設只有標成只讀（`annotations.readOnlyHint`）的工具不用確認，其他都要使用者按允許。

### 用量與額度

「系統管理 › AI 用量」（`/admin/ai-usage`）。程式在 `ai_usage.rs`。

```
GET    /api/admin/ai/usage?days=7        {defaults, running, users:[…], daily:[…], recent:[…]}
PUT    /api/admin/ai/usage/defaults      {"daily_requests","daily_tokens","max_running"}  null 是不限
PUT    /api/admin/ai/usage/users/{id}    {"daily_requests","daily_tokens","blocked"}  null 是用全站預設
```

- 每次呼叫 AI 記一筆 `ai_usage`（種類、token、工具次數、成功與否、秒數），留 400 天。
- 每天的額度以台灣時間的日期算：`chat`（送出訊息）和 `calendar`（一句話新增）各算一次；`chat_continue`（確認後接著做）和
  `title`（取標題）不算次數，token 照算。預設每人每天 50 次、300,000 tokens，有 `admin.users` 的人不受限。
  用完回 429，被停用回 403，被擋的那次不會留下訊息。
- 同一個人同時只能有一個 AI 請求；全站同時最多 `max_running` 個（預設 4，自架的 GPU 撐不了太多），滿了就請使用者稍後再試，不排隊。
  這只記在記憶體，每個容器各自算。

### 日曆：一句話新增

「日曆」和「我的事項」上方的「✨ 用一句話新增」（登入且有開放 AI 才出現）：把「下週三晚上七點跟阿明吃飯」交給
`POST /api/ai/calendar/parse`（`ai_calendar.rs`），用 `response_format` 的 JSON schema 要模型回事項的欄位，
後端檢查日期、把農曆日期換成國曆，回傳草稿打開新增事項的視窗，使用者按儲存才走原本的 `POST /api/calendar/events`。

## 聊天室

`/chat`：登入的人共用的大廳，加上知道代碼才進得來的私人房間（`loginOnly`）。後端 `backend/src/chat.rs`（訊息）、`chat_rooms.rs`（房間），前端 `frontend/src/chat/`。
正在看哪一間放在網址的 `?room=<id>`（大廳不帶），換房間不用重連。

```
GET /api/chat/ws?room=<id>                     升級成 WebSocket（要登入，沒登入會收到 unauthorized 後關閉）；room 是一開始要看的那間
GET /api/chat/messages?room=<id>&before=<id>   更早的 50 則 {room, messages, more}，舊的在前

client → server  {type:"send", room, text, nonce}   最多 2000 字；nonce 是用戶端替每則產生的編號；room 不帶是大廳
                 {type:"open", room}                 換到另一間，回 history
                 {type:"read", room, id}             私人房間看到哪一則了（未讀數用）
                 {type:"state", active, endpoint}    這個視窗有沒有人在看、這個瀏覽器的推播 endpoint（沒開通知是 null）
                 {type:"delete", id}                 刪自己的訊息，管理員、私人房間的房主可以刪任何人的
server → client  {type:"welcome", you, room, messages, more}   那間最近 50 則；要看的房間不在了就換成大廳
                 {type:"history", room, messages, more}
                 {type:"message", message:{id, room, user_id, username, text, nonce, created_at}}
                 {type:"deleted", id, room}
                 {type:"presence", users:[{id, username, active}]}
                 {type:"rooms"}                                私人房間的列表變了，重新讀 GET /api/chat/rooms
                 {type:"error", code, message, nonce?, room?}   送訊息失敗時帶著那則的 nonce；room_not_found 帶 room
```

- 訊息存在 `chat_messages`（`room_id` 是 NULL 的是大廳）；`(user_id, nonce)` 是唯一的。斷線時不知道送到了沒，重連後用同一個 nonce 重送，伺服器不會存成兩則，
  只把已經存好的那則回給送的人。重連時拿正在看的那間最近 50 則補上漏掉的（斷線期間被刪掉的也會消失）。
- 一條連線會收到自己**所有**房間的訊息（大廳加上加入的私人房間），不是正在看的那間就算成未讀，顯示在房間列表上（窄螢幕在「房間」按鈕上）。
- 右邊的「線上」列出有視窗開著聊天室的人：視窗看得到而且在前景是「在看」，切到背景、縮小、切到別的程式是「離開視窗」。私人房間改成列出成員和各自的狀態。
- 每條連線 10 秒內最多送 15 則；每 25 秒 ping 一次時順便檢查 session，登出、被停用之後連線會被關掉。
- 連線只記在記憶體，每個容器各自算：換版的幾秒內新舊容器各有一部分人，這段時間另一邊說的話要等重連才看得到，也不會推播。

### 私人房間

```
GET    /api/chat/rooms                          我加入的房間 {rooms:[Room]}，依加入的先後
POST   /api/chat/rooms              {name}      建立，自己是房主 → 201 Room
POST   /api/chat/rooms/join         {code}      用代碼加入 → Room（已經在裡面也一樣）
PATCH  /api/chat/rooms/{id}         {name}      改名（房主）
POST   /api/chat/rooms/{id}/code                換一組代碼（房主）
DELETE /api/chat/rooms/{id}                     刪掉房間和裡面的訊息（房主）
DELETE /api/chat/rooms/{id}/members/{user}      房主移出別人；user 是自己就是離開

Room = {id, name, code, owner_id, members:[{id, username}], unread, created_at}
```

- **看不到**：不是成員的人（管理員也一樣）房間列表裡沒有，用 id 讀歷史、改名、刪除一律 404（跟不存在一樣，不透露房間在不在），
  WebSocket 送進去、打開都回 `room_not_found`。房間的訊息和推播只送給成員，每則都從資料庫重新讀成員，被移出的人馬上就收不到。
- **代碼**：8 碼大寫英數字（去掉容易看錯的 0、O、1、I，共 32^8 種），畫面上顯示成 `ABCD-EFGH`，輸入時大小寫、空白、`-` 都不管。
  成員都看得到代碼、可以轉給別人；同一個人 10 分鐘內輸入錯 10 次就要等（連對的也先不收）。
- **房主**：建立的人。可以改名、換代碼（舊的馬上失效，已經在裡面的人不受影響）、刪任何人的訊息、移出成員、刪掉整間。
  移出成員時代碼會跟著換，被移出的人不能用舊代碼再進來。房主離開時交給最早加入的人；最後一個人離開，房間和訊息一起刪掉。
- 加入後看得到加入前的訊息，但不算未讀。未讀數是「看到哪一則（`chat_room_members.read_id`）之後別人說的話」，
  正在看那間而且視窗在前景時，用戶端用 `read` 回報看到最新一則。
- 每個人最多當 20 間的房主、加入 50 間；每間最多 100 人；名稱最多 30 字。
- 有人加入、離開、被移出、改名、換代碼、刪房間時，相關的人（包括被移出的人）會收到 `rooms`，重新讀列表；正在看的那間不在了就回到大廳並顯示原因。

### 通知（Web Push）

聊天室右邊的「🔔 通知」按「開啟通知」後，**聊天室開著、但沒在看的時候**有新訊息會跳出系統通知（Windows 的通知中心）。
後端 `backend/src/webpush.rs`，service worker 是 `frontend/public/push-sw.js`（範圍是整站，但沒有 fetch handler，不影響其他頁面）。

```
GET    /api/push/key             {"key"}  VAPID 公鑰（base64url）
POST   /api/push/subscriptions   PushSubscription.toJSON()  登記這個瀏覽器；同一個瀏覽器換帳號登入會改成新帳號的
DELETE /api/push/subscriptions   {"endpoint"}
POST   /api/push/test            {"endpoint"}  馬上推一則測試通知給這個瀏覽器
```

- **推給誰**（`Chat::push_targets`）：看得到這則（私人房間只有成員）、有視窗開著聊天室、但每個視窗都沒在看的人，只推到那些視窗所在的瀏覽器（連線時回報的 endpoint，
  而且必須是這個帳號自己的訂閱）。正在看的人、完全沒開聊天室的人、送出訊息的人自己都不推。
  Chrome 的「記憶體節省」把背景分頁凍結或丟掉時連線會斷，就當作沒開。
- 還沒看的訊息會合成一則通知「聊天室（3 則新訊息）」，顯示最後 4 則；私人房間的標題是「🔒 房間名稱」，每間各自合成一則。
  點通知回到聊天室的視窗，並換到那一間（已經開著的話 service worker 用 `postMessage` 叫頁面自己換，不重新載入）。
  回到聊天室時會收掉還留在通知中心、正在看的那間的通知，分頁標題前面的未讀數也會清掉。
- **VAPID**（RFC 8292）：第一次用到時產生 P-256 金鑰，存在 `site_settings` 的 `push_vapid_key`，每次推播帶 ES256 簽的 JWT，
  `sub` 是 `https://<APP_HOST>`（compose 把 `APP_HOST` 傳進容器）。換掉金鑰的話舊訂閱全部失效，前端發現公鑰不一樣會自己重新訂閱。
- 內容用 aes128gcm 加密（RFC 8291），只有那個瀏覽器解得開；加密和簽章用 rustls 本來就帶的 aws-lc-rs，單元測試比對 RFC 8291 的範例。
- 伺服器只 POST 到瀏覽器推播服務的網域（`fcm.googleapis.com`、`*.notify.windows.com`、`*.push.services.mozilla.com`、`*.push.apple.com`，
  只收 https、不跟著轉址），不能被拿來打任意網址。推播服務回 404／410 代表訂閱失效，直接刪掉；每個帳號最多 20 個瀏覽器。
- Chrome 的無痕視窗不支援 Push；iPhone 要先用 Safari「加入主畫面」，從主畫面打開才收得到。

## 部署

| 環境 | 觸發 | Image tag | 網址 |
|---|---|---|---|
| staging | merge / push 到 `dev` | `staging-<commit>`、`staging-latest` | `https://test.ouyang.app` |
| prod | merge 到 `main` | `prod-<commit>`、`prod-latest` | `https://ouyang.app` |

分支流程：

```
feature/xxx ──PR──▶ dev ──PR──▶ main
                     │            │
                  staging        prod
```

- `main` 受保護：只能透過 PR 合併，且 CI 的 `test` 必須通過，不能 force push 或刪除。
- 對 `dev` / `main` 開的 PR 只會跑測試，merge 後才會建置並部署。
- **dev → main 沿用 staging 的映像**：要進 main 的程式碼跟 dev 某次部署的一模一樣（tree 相同），
  而且 GHCR 上還有那次的 `staging-<commit>` 時，dev→main 的 PR 略過測試（`test` 照樣回報通過），
  push 到 main 時也不測、不 build，直接把那個映像加上 `prod-<commit>`、`prod-latest` 的 tag 再部署，整個流程約 1 分多鐘。
  那個映像在 push 到 dev 時已經測過、在 staging 跑過；同一個映像，所以 prod 的 `/api/health` 回的 `commit` 是 dev 那邊的 commit。
  - 照常測試和 build 的情況：main 有 dev 沒有的修改（例如直接修在 main 的 hotfix）、dev 還沒 build 完就 merge、
    那版已經被 cleanup 清掉（只留 10 版），或是手動觸發（workflow_dispatch，想強制重 build 時用這個）。
  - staging 和 prod 的 tag 指向同一個映像，cleanup 清掉其中一邊的舊版時只會拿掉那個 tag，另一邊還在用就不會被刪。

CI 的快取：
- Docker 層快取存在 GHCR 的 `buildcache-staging` / `buildcache-prod`，先讀自己環境的，沒有再讀另一個環境的。
  沒放在 Actions 快取：整個 repo 只有 10 GB，Docker 層快取一份就要好幾 GB，超過上限時 GitHub 會一直清掉舊快取。
- Rust 和 npm 的快取在 Actions 快取。Rust 快取只在 push 到 `dev` / `main` 時存，PR 只讀。
  PR 只讀得到目標分支（和預設分支 main）的快取，所以 dev→main 的 PR 讀的是 main 的，讀不到 dev 的。
  push main 沿用 staging 映像、不跑測試時，`warm-cache` job 會另外編一次測試（不跑）把 Rust 快取存回 main，
  跟 build、deploy 並行，不會拖慢 prod 部署；沒有它的話 Cargo.lock 一變，dev→main 的 PR 就要重編上百個套件。
- Dockerfile 的 cargo-chef planner 只複製 `Cargo.toml`、`Cargo.lock`、`src/`：recipe 會列出所有 target，
  `tests/` 底下多一個檔案，相依套件那層快取就會失效、全部重編（build 從約 90 秒變 250～300 秒）。
  之後如果加了 `build.rs`，planner 那段要一起複製進去。
- Rust 版本固定在 `Dockerfile` 的 `FROM rust:<版本>-bookworm@sha256:…`，CI 的 `cargo test` 也從這一行讀版本。
  不用 `rust:1-bookworm` 這種會變的 tag：它一更新 Docker 快取就全部失效，整條 Rust 重編約 4 分鐘。
  升級時版本和 digest 一起改（`docker buildx imagetools inspect rust:<版本>-bookworm` 查 digest）。
- `build` job 超過 15 分鐘會直接失敗（平常 2–5 分鐘），通常是下載 layer 卡住，重跑就好。
- CI 和 Docker build 的 `npm ci` 都設了 `ONNXRUNTIME_NODE_INSTALL=skip`：`@huggingface/transformers` 帶進來的 `onnxruntime-node`
  在 linux/x64 會從 nuget.org 下載 CUDA 的檔案，前端只在瀏覽器用不到，而且 nuget.org 連不上時 `npm ci` 會整個失敗。

### 不斷線部署（Traefik + docker-rollout）

```
外部 ─▶ Traefik :443 ─┬─ Host ouyang.app      ─▶ prod 的 app 容器
                      └─ Host test.ouyang.app ─▶ staging 的 app 容器（app 容器都不直接對外綁 port）
```

網域 `ouyang.app` 在 Cloudflare 註冊，DNS 有 `@` 和 `test` 兩筆 A 紀錄指到伺服器，都設成 **DNS only**（灰色雲朵，不經過 Cloudflare 代理）。
網址寫在 `<env>.env` 的 `APP_HOST`，app 的 router 規則是 `Host(APP_HOST)`；Traefik 的 entrypoint 名稱 `prod` 是沿用舊的，兩個環境都走這裡。
新增網域時，`traefik/compose.yaml` 的 `tls.domains` 也要加上。
HTTPS 憑證由 Traefik 向 Let's Encrypt 申請（TLS-ALPN-01，只走 :443），每個網域一張，到期前自動續約，存在 volume `ouyang-web-traefik_letsencrypt`。
不開 :80：`.app` 在瀏覽器的 HSTS 預載清單裡，瀏覽器本來就只會用 https 連。AWS 安全群組只要開 443。

之後若要開 Cloudflare 代理（橘色雲朵），先處理這幾件事：
- SSL/TLS 模式設 Full (strict)。Cloudflare 會在它那邊結束 TLS，TLS-ALPN-01 驗證不到伺服器，要改成 DNS-01（Cloudflare API token，只給這個 zone 的 DNS 編輯權限）。
- 來源 IP：`auth.rs` 的 `client_key` 取 X-Forwarded-For 最後一筆，也就是直接連進 Traefik 的那台，開代理後會變成 Cloudflare 的節點；
  只讓 Traefik 信任 Cloudflare 的 IP 範圍也不夠（Traefik 會把直接連線的 IP 接在最後）。要改成最後一筆是 Cloudflare 的 IP 時才讀 `CF-Connecting-IP`。

`deploy.sh` 用 `docker rollout` 換版：先啟動新容器 → 等 healthcheck 通過 → 再等 3 秒讓 Traefik 接上 → 停掉舊容器。

舊容器收到 SIGTERM 後不會馬上關：先讓 `/api/health` 回 503（draining），其他請求照常處理 5 秒（`DRAIN_SECS`），
Traefik 每秒主動檢查 health，看到 503 就把它移出負載平衡，之後才真正停止。換版瞬間的連線錯誤另由 retry middleware 重送。

**migration 必須跟上一版相容**：換版期間新舊兩版會同時跑在同一個 SQLite 上。
例如要改欄位名稱，分兩次部署：先加新欄位並讓程式兩邊都寫，下一版再移除舊欄位。

`/api/health` 會回傳 `commit`，可以用來確認目前是哪一版在接流量（prod 沿用 staging 映像時是 dev 那邊的 commit）。

每次部署成功後會清掉同環境的舊 image：伺服器上只留這次的加上前 2 版（`deploy.sh` 的 `KEEP_PREVIOUS_IMAGES`），
GHCR 上留最近 10 版（workflow 的 `cleanup` job，同時清掉沒有 tag 的舊版，例如被覆蓋掉的 `buildcache-*`）。

回滾：在伺服器上改 `.env` 的 `IMAGE` 再 rollout（本機現有的版本用 `docker image ls` 看，更舊的 tag 在 GitHub 的 Packages 頁面，要先 `docker login ghcr.io` 才拉得到）：

```shell
cd ~/ouyang_web/prod
sed -i 's#^IMAGE=.*#IMAGE=ghcr.io/ouyangminoa/ouyang_web:prod-<commit>#' .env
docker rollout app
```

- `SERVER_HOST`：伺服器 IP
- `SERVER_USER`：`ubuntu`
- `SSH_PRIVATE_KEY`：部署專用的 SSH 私鑰（公鑰在伺服器的 `~/.ssh/authorized_keys`）

### 伺服器上的檔案

```
~/ouyang_web/staging/   compose.yaml、staging.env、deploy.sh、traefik/（每次部署覆蓋）、.env（deploy.sh 產生）
~/ouyang_web/prod/      同上
~/ouyang_web/<env>/secrets.env   手動放的金鑰（CWA_API_KEY、HONEYPOT_AWS_*），deploy.sh 會併進 .env
```

Traefik 以固定的專案名稱 `ouyang-web-traefik` 執行，staging 和 prod 共用，所以修改 `deploy/traefik/` 會同時影響兩個環境。

資料庫在 Docker volume `ouyang-web-staging_data` / `ouyang-web-prod_data`。
